What this does

Bitbucket Cloud repository access — who can read, write to, or administer a repo, whether granted directly or through a group, at the repo level or cascading down from its Project — can change at any time, by anyone with admin rights, with no built-in history. Repo Dashboard closes that gap:

  • It scans every repository and Project in your Bitbucket workspace and records exactly who has what access.
  • Each scan is saved as a permanent, timestamped snapshot — a record of "access as of this moment" that never changes afterward.
  • You pick any two snapshots and the dashboard shows you the differences: who gained access, who lost it, and whose permission level went up or down — with escalations (e.g. read → admin) called out specifically.
  • From that same view, you can fix problems directly — lower or remove someone's access — without leaving the app.
  • You can export a point-in-time roster to a CSV file to share with a reviewer.

It runs as a local desktop app. Nothing is uploaded anywhere except the API calls it makes to Bitbucket itself; all snapshot data stays on your machine.

Getting started

Installing

Repo Dashboard is a desktop application built with Tauri. Building it yourself requires:

  • pnpm
  • Rust (stable)
  • Tauri's platform dependencies for your OS (WebKit/GTK on Linux, etc.)

From the project folder:

pnpm install pnpm tauri build # produces a distributable binary # — or, while developing — pnpm tauri dev # runs the full app with hot reload

If you were handed a prebuilt binary instead, just launch it — no installation steps beyond that.

First launch: connecting to Bitbucket

On first open, the dashboard has no data yet. Open the settings drawer (the gear icon, top right) and fill in the credentials panel:

  1. Username — your Bitbucket Cloud username.
  2. App password — a Bitbucket app password with read access to repositories, projects, and workspace membership. (Only needed for read access at this point — see the callout below for what's needed to edit access later.)
  3. Workspace — the Bitbucket workspace slug to audit (Repo Dashboard audits exactly one workspace).

Click Save credentials. The credential is stored encrypted in your operating system's keychain (macOS Keychain, Windows Credential Manager, or the Linux secret service) — it is never written to a plain file, and the app never redisplays the password once saved.

Editing permissions later needs a broader credential. The app doesn't check this upfront — everything looks the same either way, since the same credential is used for reading and writing. If your app password only has read scopes, you'll only find out when you try to apply an edit and it's rejected as unauthorized. If you plan to use the permission-editing feature, make sure the app password also has admin scope on repositories and projects.

Once connected, open the drawer again any time via Change credentials to update the username, password, or workspace.

Your first run

Still in the settings drawer, click Get all data under "run" to fetch your first snapshot. See Taking a snapshot below for what happens during this step.

Key concepts

A handful of terms recur throughout the dashboard. Understanding them up front makes the rest of the UI self-explanatory.

Principal
Whoever holds a permission — a person (identified by their stable account, not their display name, so a nickname change is never mistaken for someone leaving and a new person arriving) or a group.
Direct / Group / Member grant
Direct — a permission assigned to one person by name.
Group — a permission assigned to a group as a whole.
Member — a permission a person holds only because they belong to a group that has a Group grant. Shown separately from a Direct grant even for the same person on the same repo, since they're two different things.
Repo-level vs. Project-level
A grant can live on a specific repository, or on its Project — a Project-level grant automatically applies to every repository the Project owns. The dashboard marks Project-level rows with a "↳" prefix in the source column.
Run
A full scan of the whole workspace: every repository and Project is rediscovered from scratch and every permission is re-fetched. Produces one new snapshot.
Refresh
A narrow, targeted re-fetch of just the repos/Projects affected by a batch of edits you just applied — much faster than a full Run, but it never discovers new repositories (see Refreshing).
Snapshot
The saved result of one Run or Refresh: a complete, permanent picture of access at that moment. Snapshots are never edited after the fact, only deleted.
Baseline / Comparison
The two snapshots you're comparing. Baseline is "what it was", Comparison is "what it is now". All diffs (grants, revokes, level changes) are read as movement from Baseline to Comparison.
Grant / Revoke / Escalation / Demotion
+ Grant — access that exists in the Comparison but didn't in the Baseline.
− Revoke — access that existed in the Baseline but is gone in the Comparison.
~ Level change — the same grant exists in both, but at a different level: an Escalation if it went up, a Demotion if it went down.

Taking a snapshot ("Run now")

From the settings drawer, click Get all data. This triggers a full workspace scan:

discover every repo & Project in the workspace │ ▼ for each one: fetch direct grants, group grants, and (where resolvable) group member grants │ ▼ save everything as one new, timestamped snapshot

While it runs, a progress bar shows which repository is currently being fetched and how many remain. When it finishes, the dashboard automatically switches to comparing the new snapshot against the one before it.

If the very first step (discovering repositories) fails — e.g. your credential is rejected outright — the whole Run is aborted and nothing is saved; you'll see the error directly. If discovery succeeds but fetching one particular repo or Project fails partway through, that one repo/Project is marked fetch failed in the resulting snapshot and the rest of the Run continues normally — it isn't treated as a failed Run.

A Run always jumps you to the newest-vs-previous comparison, even if you had manually picked an older pair to look at.

Reading the dashboard

The main view is organized as Project → repository → principal. Each Project has a header with a repo/grant count; each repository is a collapsible card.

Repo cards

Each card's header shows, left to right: an expand/collapse arrow, the Project/repo path, a small admin/write/read distribution bar, a grant count ("7 grants · 2 admin"), and count badges summarizing what changed on that repo (+2 −1 ~1, or no change). Repos with at least one change open automatically when the page loads; if nothing changed anywhere in the whole comparison, every card opens instead (so you're never staring at an all-collapsed empty-looking screen).

A repo card can also carry a tag next to its name:

TagMeaning
absent from run NThis repo existed in the Baseline but is gone from the Comparison (renamed, archived, or no longer visible to the credential used).
new in run NThis repo didn't exist in the Baseline but appears in the Comparison.
fetch failedThe repo was discovered but its own permissions couldn't be fetched this Run — its grants are simply unknown, not "zero".
project fetch failedThe owning Project's own permissions call failed (independent of whether the repo's own fetch succeeded).

Rows inside a card

Each row is one principal's grant on that repo. Columns, left to right:

ColumnShows
±A sigil for the row's diff state: + grant, − revoke, ↑ escalation, ~ other level change, · unchanged.
lvlA small filled-segment meter — a quick visual read of read/write/admin level.
accessThe permission word: read, write, create-repo, or admin.
sourcedirect, group, or grp:<name> for a grant derived from group membership; prefixed with ↳ for a Project-level grant.
userThe principal's display name.
since baselineFor a changed row, the "from → to" transition (e.g. read → admin).
notesTags: escalation / escalation → admin, members unresolved (see below), or pending-edit tags.

members unresolved appears on a group's own row when the group's permission was fetched successfully but its member list could not be (typically an app-password scope issue) — in that case no individual member rows are shown for that group at all, since there's no way to know who they are.

Note on "create-repo". Bitbucket has a fourth permission level, project-scope only, between write and admin. It's shown as its own distinct word wherever a level is displayed, but for the purposes of counting changes and deciding escalation/demotion, it's treated as equivalent to admin — so a create-repo ↔ admin change never shows up as a diff.

Comparing two runs

The top bar has two selectors, baseline and comparison, each listing every recorded run by number and date (run 1 is always the very first run ever taken). Change either selector to change what's being compared; use the ⇄ button to swap them.

Selecting the same run for both is allowed — it just shows that run's roster with no diff markers, which is a normal way to browse current access without comparing to history.

Next to the selectors, a note like 14 days apart · 82 → 91 grants (or single run · 82 → 82 grants when both sides match) gives a quick sense of scale, and a row of chips on the right summarizes the diff: +3 added −1 revoked ~2 changed plus a separate ↑N escalations chip when any level change went up. If nothing changed at all, a single no change chip appears instead.

Filtering and expanding

The bar just under the header offers two tabs:

  • All access — every grant in the Comparison snapshot, changed or not.
  • Changes only — just the rows that differ from the Baseline; repos with zero changes disappear entirely from the list.

Next to the tabs: a live count (N live · N changed · N rows), an Expand all / Collapse all toggle (its label always reflects what clicking it will do, scoped to whatever's currently visible under the active tab), and Reset, which returns to the All access tab and clears every manual expand/collapse you made.

If a filter leaves nothing to show, an empty-state message explains why — either "no permission changes between run X and run Y" (with a button to switch to All access), or a generic "nothing matches these filters" (with a button to reset).

Changing or removing access

From the Comparison snapshot's roster — but only while that snapshot is the most recent one recorded — you can edit access directly from the dashboard, without going to Bitbucket.

Editing is only available when the Comparison you're viewing is the latest snapshot. If you've picked an older run to compare against, the row menus (⋯) simply aren't there — editing against a historical view would be changing the present based on a look at the past.

What can be edited

  • Any Direct grant (a specific person's own permission) — at repo or Project scope.
  • Any Group grant (the group's own permission) — at repo or Project scope.
  • Member rows (access derived from group membership) have no edit menu at all — to change them, edit the underlying group's own grant instead.

Granting access to someone who currently has none isn't supported yet — editing only covers changing or removing an existing grant.

Staging a change

  1. Click the ⋯ menu at the right of a row.
  2. Pick a new level (Read / Write / Admin) to stage a level change, or ✕ Remove access to stage a removal. Re-selecting the row's current level cancels the staged edit instead of doing nothing.
  3. If you're removing a group's grant, the menu warns you how many people's access is derived from it and would disappear too (e.g. "removing this also drops access for 3 members") — group-derived (Member) access has no separate on/off switch, so removing the group's own grant removes all of it at once.

Staged rows are marked pending · unsaved or pending removal and preview the change immediately (struck-through for a removal). Nothing is sent to Bitbucket yet. Click ↺ undo on a staged row to discard just that one change.

You can stage as many changes as you like across different repos before applying anything.

Applying

Once at least one change is staged, an Apply N changes button appears in the top bar. Clicking it opens a confirmation dialog listing every staged change (repo, person, from → to level, and any cascade warning), for one final review before anything actually happens.

Click Confirm to send the whole batch to Bitbucket. Each change is applied independently — one failing (e.g. insufficient credential scope, the grant was already changed elsewhere, or rate limiting) does not block the rest of the batch. The results view shows a ✓/✕ status per row, with a reason for any failure:

FailureMeaning
credential lacks the required scopeYour app password doesn't have admin rights on that repo/Project.
rate limited — retryBitbucket throttled the request; try applying again shortly.
(other message)Whatever error Bitbucket returned verbatim.

Anything that failed stays staged in the dashboard for you to retry later; anything that succeeded is cleared from the pending list.

Applying changes Bitbucket's live permissions — it does not change the snapshot you're looking at. A snapshot never updates itself; the dashboard will keep showing the old numbers until you take a new Run or Refresh (below).

Any staged-but-not-yet-applied edits are silently discarded (not carried forward) if a new Run or Refresh completes, or if you switch the Comparison to a different snapshot — either way, the snapshot they were staged against is no longer the one on screen.

Refreshing after a change

Right after applying a batch (in the results view), if at least one edit succeeded, a Refresh affected button appears. This is a fast way to see your edits reflected without a full Run:

  • It creates one new snapshot by copying every repo/Project untouched by your batch straight from the snapshot you edited against.
  • It only re-fetches live data for the specific repos (or, for a Project-scope edit, every repo that Project owns) your successful edits touched.
  • It does not rediscover the workspace — if a repo was created, deleted, or moved between Projects since your last Run, only a full Run will pick that up.

On success, the dialog closes, remaining pending edits are cleared, and the new snapshot is automatically selected as the Comparison (your Baseline selection is left alone).

Closing the results view instead (without refreshing) retires that opportunity — you'd need a full Run to see the change reflected afterward.

Exporting a CSV roster

Click Export in the filter bar to save a CSV file of the current Comparison snapshot's full roster.

  • Always the Comparison snapshot alone — never a diff, and unaffected by whatever Baseline or view filters are currently active on screen.
  • One row per grant: repo project, repo, principal id, display name, access type (direct / group / member:<group>), scope (repo / project), permission level, and the run's timestamp.
  • You'll be prompted with a native Save dialog; the suggested filename is roster_<workspace>_<timestamp>.csv.

This is meant for a one-off share or archive — the dashboard itself remains the source of truth for ongoing auditing, not the CSV.

Managing snapshots

The settings drawer's snapshots panel lists every run ever recorded, newest first. Click Delete next to one, then Confirm to permanently remove it (or Cancel to back out).

Deleting a snapshot is permanent. If you delete the snapshot currently selected as Baseline or Comparison, the dashboard falls back to comparing the newest remaining run against the one before it — the same default it uses on first load.

Appearance

The settings drawer's appearance panel switches between Light and Dark themes. The choice applies immediately and persists between sessions.

FAQ / troubleshooting

Nothing happens when I click "Get all data"

Check that credentials are saved (the drawer's credentials panel should read "connected as ... on ..."). If a Run fails outright with an error, it's most likely that Bitbucket rejected the credential itself (e.g. wrong password, or the app password lacks basic workspace-read scope) — in that case no snapshot is saved at all.

A repo shows "fetch failed" — is my data wrong?

No — a fetch failure means the tool doesn't yet know that repo's permissions for this Run; it's tracked separately from "this repo genuinely has zero grants." Re-running (or refreshing, if the failure is on an edited repo) will attempt the fetch again.

Why can't I edit permissions on a snapshot I'm viewing?

Editing is only offered when the Comparison snapshot is the newest one on record. Select the latest run as your Comparison to get edit menus back.

Why don't I see any member rows under this group?

Either the group truly has no members, or its membership couldn't be fetched (usually a scope limitation on the app password) — in the latter case the row is tagged members unresolved and no member rows are shown, since the tool has no way to know who they'd be.

I applied an edit and the dashboard still shows the old permission

That's expected — applying pushes the change to Bitbucket, but a snapshot is immutable and never updates itself. Use Refresh affected from the apply results view, or take a new full Run, to see it reflected.

My apply failed with "credential lacks the required scope"

Editing permissions requires broader Bitbucket app-password scopes (repository/project admin) than just viewing them does. Update the app password's scopes in Bitbucket, save the new password in the credentials panel, and retry — the failed edit stays staged for you.

Can I audit more than one Bitbucket workspace?

No — one configured workspace at a time. Switching workspaces means changing the workspace field in the credentials panel and taking a new Run.

Is this connected to any notifications or alerts?

No. It's a pull-based tool — you open it and compare runs yourself; nothing pushes alerts to you.

Glossary

Principal
A user or a group that can hold a permission grant.
Grant scope (Repo / Project)
Whether a grant lives on the repository itself, or on its Project (cascading to every repo the Project owns).
Direct grant
A permission assigned to one person individually.
Group grant
A permission assigned to a group as its own entity.
Member grant
A permission a person holds by virtue of belonging to a group with a Group grant; not separately editable.
Run
A full workspace scan (rediscovers every repo/Project) that produces one new snapshot.
Refresh
A narrow re-fetch of just the repos/Projects touched by a just-applied edit batch; produces a new snapshot but never rediscovers the workspace.
Snapshot
One immutable, timestamped Run or Refresh's worth of data across the workspace.
Baseline / Comparison
The earlier ("what it was") and later ("what it is now") snapshot in the pair being compared.
Grant / Revoke
Access that appears / disappears between Baseline and Comparison.
Escalation / Demotion
A grant's level going up / down between Baseline and Comparison.
Pending edit
A staged, not-yet-applied change to a Direct or Group grant, held locally until you click Apply.
Apply
Sending every currently staged edit to Bitbucket as live permission changes.
Unresolvable membership
A group whose own grant was fetched but whose member list couldn't be — no Member rows are derived for it that Run.
