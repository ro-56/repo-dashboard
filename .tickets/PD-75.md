## Context

From the 2026-08-01 architecture review (candidate 1, \"Strong\"): `pending`, `editingEnabled`, `onStage`, `onUndo` are threaded unchanged through `+page.svelte` → `ProjectSection.svelte` → `RepoCard.svelte` → `RosterRow.svelte`, but only `RosterRow.svelte` ever reads or writes them (`src/lib/components/RosterRow.svelte:6-29`). `ProjectSection` and `RepoCard` are pure conduits for these four props (`ProjectSection.svelte:9-31,53-65`, `RepoCard.svelte:18-45,102-112`). Same pattern for `projectPrincipals`: computed once in `ProjectSection.svelte:41`, passed untouched through `RepoCard.svelte:107`, consumed only in `RosterRow.svelte:39`.

Deletion test: removing the intermediate props and having `RosterRow` reach into a shared seam instead wouldn't concentrate complexity anywhere new — `ProjectSection`/`RepoCard` genuinely have nothing to do with editing.

## What to explore

Design a seam (Svelte context is the natural fit, given Svelte 5 runes) that bundles `pending`/`editingEnabled`/`onStage`/`onUndo` (and possibly `projectPrincipals`'s consumer-side derivation) so `RosterRow` reads it directly, without `ProjectSection`/`RepoCard` declaring or forwarding any of these props.

Before implementing:
- Confirm whether `projectPrincipals` belongs in the same context or should stay a prop (it's computed per-ProjectSection from repo data, not top-down state like the editing fields — worth a grilling pass on whether bundling it in is the right call or conflates two different kinds of data).
- Check for any other consumer of these props further down the tree (e.g. does `RosterRow` ever get instantiated standalone in a test, and would a context requirement break that test setup?).
- Decide the context's exact shape (one object vs. several context keys) — see `/codebase-design` on interface simplicity.

## Acceptance criteria

- [ ] `ProjectSection.svelte` and `RepoCard.svelte` no longer declare `pending`/`editingEnabled`/`onStage`/`onUndo` props.
- [ ] `RosterRow.svelte` obtains editing state via a defined seam (context or equivalent), not prop drilling.
- [ ] Existing `rosterRow.test.ts` / `pendingEdits.test.ts` coverage still passes; component behavior unchanged (staging, undo, cascade-count menu) — verify manually via `pnpm tauri dev`.
- [ ] No new prop threading introduced elsewhere as a side effect.
