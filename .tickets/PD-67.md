## What to build

The head bar's global Apply button currently always renders, disabled via a `disabled` attribute when there's nothing staged. Change it to full conditional rendering: the button is absent from the DOM entirely unless there is at least one staged Pending edit AND editing is currently enabled (Comparison is the latest Snapshot, per ADR-0022).

Add a pure function `canApply(pendingCount: number, editingEnabled: boolean): boolean` to `headBar.ts`, returning `true` only when `pendingCount > 0 && editingEnabled`. `+page.svelte` replaces its inline `applyDisabled` derived value with a call to `canApply`, passed to `HeadBar` as a prop named `canApply` (renamed from `applyDisabled`, sense inverted). `HeadBar.svelte` wraps the `.apply-btn` element in `{#if canApply}` instead of setting `disabled`; the `disabled` attribute and `.apply-btn:disabled` CSS are removed. `openApplyDialog()`'s existing guard clause becomes `if (!canApply) return;` and is retained as defense-in-depth.

Full decision rationale lives in PD-66.

## Acceptance criteria

- [ ] `canApply(pendingCount, editingEnabled)` exists in `headBar.ts`, returning `true` only when both `pendingCount > 0` and `editingEnabled` are true
- [ ] `headBar.test.ts` covers all four combinations of `pendingCount` (zero / non-zero) × `editingEnabled` (true / false)
- [ ] `+page.svelte` computes and passes `canApply` (not `applyDisabled`) to `HeadBar`
- [ ] `HeadBar.svelte`'s Apply button is wrapped in `{#if canApply}` — absent from the DOM, not just disabled, when `canApply` is false
- [ ] `.apply-btn:disabled` CSS and the `disabled` attribute are removed from `HeadBar.svelte`
- [ ] `openApplyDialog()`'s guard clause is updated to `if (!canApply) return;`
- [ ] `pnpm test` passes
- [ ] Manually verified via `pnpm tauri dev`: button appears when an edit is staged, disappears when undone, stays absent on an older Run pair, and disappears along with discarded edits after a new Run completes
