## What to build

Add an optional Justification to a staged permission edit, and durably persist it — along with who applied it and when — the moment that specific edit is successfully applied to Bitbucket. This is the backend + wire-contract half of PD-87: no UI capture yet (that's the follow-up ticket), but the full plumbing is real and test-covered end to end.

- `PendingEditRequest`/`StagedEdit` (both `src-tauri/src/apply.rs` and `src/lib/pendingEdits.ts`) gain a new optional `justification` field (`Option<String>` / `string | undefined`), serialized camelCase on the wire like the rest of the struct.
- A new SQLite table — the Applied-edit log — is added to `storage.rs`'s existing lazy `CREATE TABLE IF NOT EXISTS` schema block. One row per **successfully applied** edit: repo/project, repo, Principal id/label, target (Direct or Group), scope (Repo/Project), action (SetLevel-to-level or Remove), before-level, after-level (nullable for Remove), `justification` (nullable text, soft max 500 chars enforced at the frontend), `applied_at` (RFC3339 string, same format `run_at` already uses), and `account` (verbatim from stored `Credentials.username` — labeled "account," never claimed as a verified email; no schema change to `Credentials`).
- Deliberately **no** `source_snapshot_id` column or foreign key into `snapshots` (ADR-0032) — the log must survive Snapshot deletion (ADR-0011) unconditionally.
- `apply::apply_pending_edits` is extended to accept a `&mut rusqlite::Connection`, `applied_at: &str`, and `account: &str` alongside its existing `client`/`workspace`/`edits` params (mirroring how `collect_and_store`/`refresh_and_store` already take a connection + timestamp). After computing each edit's `ApplyResult`, it writes an Applied-edit log row for every success — nothing for a failure (`Unauthorized`/`RateLimited`/`Other`); a failed edit stays staged for retry with its Justification intact, and only gets logged if a later retry succeeds. The function still returns the same `Vec<ApplyResult>` shape as today.
- `lib.rs`'s `apply_pending_edits` Tauri command becomes a thin wrapper: it additionally takes `db: tauri::State<'_, DbState>`, computes `applied_at` via `chrono::Utc::now().to_rfc3339()`, reads `account` from the already-fetched `creds.username`, and passes both plus a locked `conn` down into `apply::apply_pending_edits`.
- `pendingEdits.ts`'s `confirmRows`/`resultRows`/`toApplyPayload`/`ConfirmRow`/`ResultRow` thread the `justification` field through so later UI work (PD-87's Ticket 2) can display it without further plumbing changes.

## Acceptance criteria

- [ ] `PendingEditRequest`/`StagedEdit` carry an optional `justification` field on both the Rust and TS sides, wire-compatible (camelCase).
- [ ] A new Applied-edit log SQLite table exists with the column set above, created via the same lazy `CREATE TABLE IF NOT EXISTS` pattern as the rest of `storage.rs`, with no foreign key to `snapshots`.
- [ ] `apply::apply_pending_edits` writes exactly one Applied-edit log row per successfully-applied edit, and zero rows for failed edits.
- [ ] A batch mixing successes and failures logs only the successes, each with the correct before/after level, justification text (or null if none was staged), `applied_at`, and `account`.
- [ ] Deleting every Snapshot (`delete_snapshot`) has no effect on existing Applied-edit log rows (regression check).
- [ ] `cargo test` covers: successful SetLevel with a justification; successful Remove with no justification; a failed edit produces no log row; a mixed batch logs only successes; `applied_at`/`account` are recorded verbatim from the parameters passed in.
- [ ] `pendingEdits.test.ts` covers: an edit staged with/without a Justification round-trips correctly through `confirmRows`/`resultRows`/`toApplyPayload`; a missing Justification serializes as absent/undefined, not an empty string.
- [ ] No user-visible UI change in this ticket — any edit staged through the existing app still stages with `justification: undefined`, since no input exists yet to set it.
