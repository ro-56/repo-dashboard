## What to build

Thread a live progress signal through `collect_and_store` and out through `run_now`, so the frontend can eventually show which repo is currently being fetched and how far through the Run we are. This ticket is backend-only — no UI change yet.

Add a `RunProgress { index: u32, total: u32, repo: String }` type (`index` 1-indexed) and a `progress: &mut impl FnMut(RunProgress)` parameter to `collect_and_store`, per ADR-0013 (`docs/adr/0013-run-progress-via-injected-callback.md`) — this keeps the function Tauri-free and fully covered by `cargo test`, mirroring the existing `BitbucketClient`/`FakeBitbucketClient` pattern.

Call `progress` exactly once per repo in the main discovery loop, immediately before that repo's own calls begin. `total` is the repo count from discovery, computed once before the loop and unchanged on every call. A repo's Project-level fetch (only triggered for the first repo of a given Project in this Run, via the existing `project_cache`) is folded silently into that repo's single tick — never reported as its own event. No call to `progress` happens during discovery itself, and a repo-level `FetchFailed` does not change what gets passed for that repo (the callback only ever carries `{index, total, repo}`, never a status).

Wire `run_now` (`lib.rs`) to pass a closure that calls `app_handle.emit("run-progress", progress)`. No other change to `run_now`'s control flow, error mapping, or return type.

## Acceptance criteria

- [ ] `RunProgress { index, total, repo }` type exists and is passed through a `progress: &mut impl FnMut(RunProgress)` parameter on `collect_and_store`.
- [ ] `progress` is called once per repo, 1-indexed, immediately before that repo's fetches start.
- [ ] A repo that triggers its Project's first-time fetch in this Run still produces exactly one `RunProgress` call for that repo — never a separate call for the Project.
- [ ] No `RunProgress` call happens before discovery resolves.
- [ ] A repo-level `FetchFailed` does not suppress or alter that repo's `RunProgress` call, and the Run continues reporting progress for subsequent repos as before.
- [ ] A mid-Run abort (`CredentialRejected`) produces no further `RunProgress` calls after the point of failure; a `DiscoveryFailed` abort produces none at all.
- [ ] `run_now` emits a `run-progress` Tauri event via `AppHandle::emit` using this callback; `run_now`'s signature, return type, and existing error mapping are unchanged.
- [ ] `cargo test` in `src-tauri` covers all of the above by capturing the sequence of `RunProgress` values into a `Vec` via a test closure, extending the existing `collect.rs` test module (FakeBitbucketClient pattern) rather than adding a new test seam.
