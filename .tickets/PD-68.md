## Problem Statement

After applying a batch of permission edits (PD-59/60/61/62), the dashboard has no way to show the result except telling the user to trigger a full Run — a workspace-wide repo discovery plus a fetch of every single repo and Project, even when the edit batch only ever touched a handful of them. For a workspace with hundreds of repos, confirming a one-line permission change costs the same as auditing the entire workspace from scratch. Users need a fast, narrow way to see their own just-applied changes reflected without paying that cost, while everything they didn't touch stays exactly as their last full Run recorded it.

## Solution

Add **Refresh**: a new action offered in the Apply results view, right after a batch of Pending edits is applied. Refresh creates one new Snapshot by copying every repo and Project untouched by that batch verbatim from the source Snapshot (the one the batch's edits were staged against), and re-fetching live data only for the **Refresh targets** — the specific repos (for Repo-scope edits) or Projects (for Project-scope edits, cascading to every repo the source Snapshot already records under that Project) named by the batch's *successful* edits. Refresh never calls repo discovery; a full Run remains the only way to pick up a repo that was created, deleted, or moved between Projects. Refresh fires immediately (no confirm step — it only reads), clears any remaining staged Pending edits exactly as a Run does, and auto-selects its new Snapshot as the Comparison so the applied change is visible without further clicks. Full ADR and glossary detail: `docs/adr/0025-refresh-targeted-snapshot-without-discovery.md`, `CONTEXT.md` (**Refresh**, **Refresh target**).

## User Stories

1. As an auditor, I want to see my applied permission changes reflected without running a full workspace scan, so that I can confirm my edits quickly.
2. As an auditor, I want a "Refresh affected" option to appear right in the Apply results view, so that I don't have to hunt for it elsewhere.
3. As an auditor, I want Refresh to only re-fetch the repos/projects I actually edited, so that confirming a one-repo change doesn't cost a full workspace re-scan.
4. As an auditor, I want a Repo-scope edit to only re-fetch that one repo's grants, so that Refresh stays fast and narrow.
5. As an auditor, I want a Project-scope edit to refresh every repo already known to belong to that Project, so that the cascading nature of Project grants is reflected everywhere it applies.
6. As an auditor, I want edits that failed to apply to be excluded from what Refresh re-fetches, so that I'm not wasting a fetch confirming data that never changed.
7. As an auditor, I want every repo/project untouched by my edits to remain exactly as it was in my last full Run, so that Refresh never accidentally introduces unrelated changes into my audit trail.
8. As an auditor, I want Refresh to fail safely if my credential is rejected mid-refresh, so that I never end up with a half-written or misleading Snapshot.
9. As an auditor, I want a single unreachable repo/project during Refresh (rate-limited, or some other error) to not block the rest of the refresh, so that one flaky call doesn't waste my whole confirmation attempt.
10. As an auditor, I want a repo/project that failed to refresh to show the same "fetch failed" signal I already know from full Runs, so that I don't have to learn a second, different failure state.
11. As an auditor, I want group membership to be freshly resolved for any group grant I touched, so that Member grants shown after Refresh are accurate, not stale.
12. As an auditor, I want any Pending edits still staged after a partial Apply failure to be cleared once I Refresh, so that I'm never staging changes against a Snapshot that's no longer current.
13. As an auditor, I want the dashboard to automatically show my refreshed Snapshot as the Comparison, so that I see my applied changes the moment Refresh finishes, without extra clicks.
14. As an auditor, I want Refresh to fire immediately without a second confirmation dialog, so that confirming my own already-reviewed edit isn't slowed by a redundant prompt.
15. As an auditor, I want Refresh to only be offered right after the Apply it corresponds to, so that I'm never confused about which batch of edits a "Refresh" button refers to.
16. As an auditor, if I dismiss the Apply results view without refreshing, I want a full Run to still be available as my path to see the change, so that I'm never stuck without a way to confirm my edits.
17. As an auditor editing several repos in one batch, I want all of them refreshed together in one click, so that I don't have to refresh repo-by-repo.
18. As an auditor who edited the same repo twice in one batch (e.g. two different principals), I want that repo refreshed only once, so that Refresh doesn't waste duplicate calls.
19. As an auditor who both edited a Direct grant on one repo and a Group grant on a Project in the same batch, I want both dimensions correctly refreshed — the one repo's Direct data and the whole Project's cascaded Group data — so that a mixed batch is fully reflected.
20. As an auditor, I want a repo that is both directly edited (Repo scope) and inside an edited Project (Project scope) to have both its Repo-scope and Project-scope data refreshed, so that neither dimension is left stale.
21. As an auditor, I want Refresh to never call repo discovery, so that a repo created, deleted, or moved between Projects since my last full Run isn't silently picked up or dropped by something that's supposed to be narrow and predictable.
22. As an auditor, I want a Refresh-produced Snapshot to look and behave exactly like any other Snapshot (deletable, diffable, selectable), so that I don't need to learn special rules for it.
23. As an auditor, I want to be told clearly if my credential was rejected during Refresh, mirroring how a Run reports the same failure, so that I recognize the problem immediately.
24. As an auditor whose entire batch failed to apply, I want the Refresh option to be unavailable, so that I'm not offered a no-op action.
25. As an auditor, I want historical Snapshots I'm not currently comparing against to remain untouched by a Refresh, so that my audit trail is never retroactively altered.
26. As a developer maintaining this codebase, I want Refresh's core logic to live in one pure, cargo-testable module following the same shape as `collect_and_store` and `apply_pending_edits`, so that the three orchestration paths stay consistent and easy to reason about.
27. As a developer, I want the frontend's Apply-result-to-Refresh-payload logic to live in the existing `pendingEdits.ts` module rather than a new file, so that Apply/Refresh's related logic stays colocated.

## Implementation Decisions

- New Rust module `refresh.rs`, exposing `refresh_and_store<C: BitbucketClient>(client: &C, conn: &mut Connection, workspace: &str, source_snapshot_id: i64, run_at: &str, results: &[ApplyResult]) -> Result<i64, RefreshError>` — same shape as `collect_and_store` (`collect.rs`) and `apply_pending_edits` (`apply.rs`). Owns all meaningful logic; the Tauri command is a thin wrapper only.
- `RefreshError` enum: `CredentialRejected`, `StorageFailed(String)`. No `DiscoveryFailed` variant — Refresh never calls `list_repositories`.
- Target derivation: filter `results` to `Ok` outcomes only; dedupe into two sets keyed on `(GrantScope, repo_project, repo)` — a `repo` target set (Repo-scope edits) and a `repo_project` target set (Project-scope edits). Multiple edits addressing the same repo/project in one batch collapse to a single fetch for that entity.
- Loading the source Snapshot: reuse `storage::load_snapshot` (records + repo_fetch_statuses), `storage::load_project_fetch_statuses`, and `storage::load_group_membership_statuses` — all pre-existing.
- Copy-forward + replace: records/statuses belonging to a targeted repo's Repo-scope dimension, or to a targeted Project's Project-scope dimension (across every repo the source Snapshot already records under that Project), are dropped from the copied set and replaced with freshly fetched data. Everything else is copied unchanged.
- Repo-scope target refresh: refetch `list_direct_permissions` + `list_group_permissions` (+ `list_group_members` per encountered group, cached per-refresh-call the same way `collect_and_store` caches per-Run) via the existing `normalize_repo_permissions`/`normalize_repo_group_permissions`, mirroring `collect_and_store`'s per-repo block exactly.
- Project-scope target refresh: refetch `list_project_direct_permissions` + `list_project_group_permissions` (+ member resolution) once per Project via `normalize_project_permissions`/`normalize_project_group_permissions`, then apply the resulting Project-scope records to every repo the *source Snapshot* already records under that `repo_project` — never a fresh discovery call to redetermine Project membership (ADR-0025).
- Failure handling, per target: `ClientError::Unauthorized` aborts the whole Refresh immediately — `RefreshError::CredentialRejected`, no Snapshot written. `RateLimited`/`Other` on one target records that target's status as `FetchFailed` (a single `ProjectFetchStatus` row for a Project target, not duplicated per repo) with zero PermissionRecords for that scope/entity — identical to `collect_and_store`'s convention — and Refresh continues with remaining targets.
- Persistence: assemble the merged `records`/`repo_statuses`/`project_statuses`/`group_membership_statuses` and persist via the existing `storage::save_snapshot`, unmodified.
- Tauri command `refresh_snapshot(source_snapshot_id: i64, results: Vec<ApplyResult>) -> Result<i64, String>` in `lib.rs`: thin wrapper following the `run_now`/`apply_pending_edits`/`delete_snapshot` convention — generates `run_at` via `chrono::Utc::now().to_rfc3339()`, stringifies `RefreshError` for the frontend, no independent test coverage beyond the underlying module.
- Frontend `pendingEdits.ts` additions: a pure function to filter `ApplyResult[]` down to `Ok` outcomes / gate Refresh's availability (used both to enable/disable the new button and to build the exact `results` payload sent to `invoke("refresh_snapshot", ...)`). No new TS module.
- `ConfirmApplyDialog.svelte`: results phase gains a second button, "Refresh affected", next to "Close" — disabled when no result in the batch succeeded. Clicking it invokes `refresh_snapshot`, then on success: closes the dialog, clears all Pending edits (reusing the existing clear-on-run-completion hook, not a parallel implementation), refreshes the snapshot list, and auto-selects the new Snapshot id as Comparison.
- No confirm dialog for Refresh itself — it only performs reads.

## Testing Decisions

Tests should verify externally observable behavior (inputs/outputs of the seam), not internal control flow — following the existing `collect.rs`/`apply.rs` fake-client pattern, where tests assert which client methods were called, with what arguments, and what result came back.

- `cargo test` in `src-tauri`, new `refresh.rs` test module, using a fake `BitbucketClient` (following the exact per-module fake-client convention already used in `collect.rs` and `apply.rs`):
  - A Repo-scope target refreshes only that repo's Direct/Group data; everything else is copied verbatim from the source Snapshot.
  - A Project-scope target refreshes every repo the source Snapshot already records under that Project, via one Project-level fetch (not one per repo).
  - A batch with duplicate targets (same repo/project addressed by more than one edit) fetches that entity only once.
  - A mixed batch (Repo-scope edit on one repo + Project-scope edit on an unrelated Project) refreshes both dimensions independently and correctly.
  - A repo that is both a direct Repo-scope target and part of a targeted Project has both its Repo-scope and Project-scope data refreshed.
  - Failed (`Err`) `ApplyResult`s contribute no target and are excluded from the fetch entirely.
  - A 401 on any target aborts the whole Refresh with no Snapshot written.
  - A non-401 failure on one target records `FetchFailed` (zero records) for just that target and the rest of the Refresh completes normally.
  - Group membership is resolved live (via the fake's `list_group_members`) for touched groups, not copied from the source Snapshot.
  - An empty target set (all results failed, or an empty `results` slice) produces a Snapshot that is an exact copy of the source.
- Colocated `pendingEdits.test.ts` (vitest) additions: covers the new Ok-filtering/availability-gating function's behavior on an all-failed batch, an all-succeeded batch, and a mixed batch.
- No new Playwright/component-rendering tests (ADR-0017, still deferred). The "Refresh affected" button, snapshot-list update, Comparison auto-select, and pending-edit-clearing behavior are verified manually via `pnpm tauri dev`.

## Out of Scope

- Detecting a repo added to, removed from, or moved between Projects since the last full Run — a Project-scope Refresh always uses the Project's repo membership as already recorded in the source Snapshot (ADR-0025). Only a subsequent full Run picks this up.
- Any marker/badge distinguishing a Refresh-produced Snapshot from a Run-produced one, in snapshot lists, history, or storage — they are stored and displayed identically.
- Auto-triggering Refresh without an explicit user click, under any Apply outcome (including a fully successful batch).
- Carrying forward or auto-retrying failed edits after a Refresh — they are cleared exactly like a Run clears them (ADR-0022), not preserved for retry.
- A persistent, head-bar-level "Refresh last edited repos" action reachable outside the Apply results view it was produced by.
- Any change to `apply_pending_edits`'s own behavior, routing, or error semantics — Refresh is purely additive downstream of it.
- Modeling `create-repo` or `none` permission levels, or any other change to the permission-editing scope boundaries already set by ADR-0021/ADR-0024.
