## Problem Statement

When auditing the Roster tree, some Principals are permanent noise for a given analysis — a service account, a CI bot, an Auditors group whose access is expected and never interesting — and they clutter every repo card regardless of which Snapshots are being compared. Principal search (`CONTEXT.md`'s **Principal search**, PD-85/PD-86) already narrows the tree to a *positive* match, but there's no way to do the opposite: durably (for the length of this analysis session) suppress specific Principals so they stop appearing at all, without having to remember to avoid looking at them.

## Solution

A session-scoped **reverse filter** — "Excluded principal", now a confirmed `CONTEXT.md` glossary entry — lets the user hide specific Principals (by stable identity, not label text) from the Roster tree for the rest of the current session. It composes with the two existing screen filters (view mode, Principal search) as a third AND-ed condition, using the same repo-disappears / counts-recompute machinery already built for search. It's added via a quiet "Hide" link revealed on hover next to each row's existing `⋯` menu (a sibling trigger, not a new item inside that menu), and managed (viewed/removed/cleared) via a slim banner that appears atop the tree once ≥1 Principal is hidden.

## User Stories

1. As an auditor reviewing a workspace with a noisy service-account group, I want to hide that group's rows for this session, so that I can focus on the Principals I actually need to review without it re-appearing on every repo card.
2. As an auditor, I want to hide more than one Principal at a time, so that I can suppress several known-noisy accounts/groups at once rather than one at a time.
3. As an auditor, I want exclusion to be based on the Principal's real identity rather than their display name, so that a nickname change mid-session can't accidentally un-hide (or wrongly hide) the wrong person.
4. As an auditor who excludes a noisy group, I want every user's Member grant derived from that group to disappear too, so that hiding "Auditors" actually clears the noise its membership creates, not just the group's own row.
5. As an auditor who excludes a group that one of its members also holds a personal Direct grant on, I want that unrelated Direct grant to stay visible, so that excluding the group doesn't accidentally hide a real, independent grant that happens to belong to the same person.
6. As an auditor, I want exclusion to combine with the existing All access/Changes only tab and Principal search, so that all three filters narrow the same tree together rather than fighting each other.
7. As an auditor, I want a repo whose only rows are excluded to disappear from the tree entirely, so that I'm not left staring at an empty card.
8. As an auditor, I want the "N live · N changed · N rows" count to reflect only what's actually on screen, so that it never disagrees with what the exclusion filter is showing me.
9. As an auditor, I want the existing Reset control to also clear my exclusions, so that there's one single "back to blank slate" action rather than two different reset behaviors to remember.
10. As an auditor looking at a specific noisy row, I want to hide that Principal directly from the row itself, so that I don't have to leave the row to go find a separate control.
11. As an auditor, I want a single place to see everything I currently have hidden, so that I don't lose track of an exclusion I set earlier in the session.
12. As an auditor, I want to remove a single exclusion individually, so that I can un-hide one Principal without clearing everything else I've excluded.
13. As an auditor, I want to clear every exclusion at once from that same place, so that I have a fast bulk option distinct from the row-by-row removal.
14. As an auditor, I want the exclusion list and its controls to look and feel consistent with the row menu already in the app, so that the feature doesn't feel bolted on.

## Implementation Decisions

- **Persistence/lifecycle**: Session-scoped only, matching Principal search's lifecycle exactly — lives in local UI state, cleared by the existing `FilterBar` Reset control, never persisted to disk/SQLite, not staged against or carried by any Snapshot, and survives Baseline/Comparison navigation the same way view mode and search already do.
- **Match basis**: Exact `principal.id` identity, never label-text substring matching. This is a deliberate departure from Principal search's substring-on-label approach — identity is stable, per `CONTEXT.md`'s existing "identity is always the stable id, never the user-editable label" rule for Principal itself.
- **Exclusion (cascade) rule**: an entry is hidden if **either**:
  - its own `entry.principal.id` is in the excluded-id set, **or**
  - it's a `Member` entry whose `accessType.group_id` is in the excluded-id set (cascade from an excluded group's own grant).

  This means excluding a Group hides the Group's own row plus every `Member` row derived from it, but does **not** hide an unrelated `Direct` (or other `Group`) entry belonging to the same person — each `PrincipalEntry` is matched independently. Excluding a user (not a group) hides every entry carrying that user's own `principal.id`, which naturally includes their `Direct` grants and any `Member` grants they hold via *any* group, since those all carry the user's own id. Recorded as ADR-0032, `docs/adr/0032-excluded-principal-group-cascade-scoped-to-member-rows.md`.
- **Composition with existing filters**: folds in as a third AND-ed condition alongside view mode and search on the existing `isEntryVisible` (`filterBar.ts`) — a row shows only if it passes view mode AND search AND is not excluded. `visibleRepos`/`viewCounts` need no new mechanism: a repo disappears once zero rows pass all three conditions (same rule already governing search), and the "N live · N changed · N rows" count recomputes over exactly what's left, exactly as it does today for search.
- **Reset**: the existing `FilterBar` Reset control also clears the exclusion set, in addition to search text and expand/collapse overrides it already resets.
- **Adding an exclusion — row hover link**: `RosterRow.svelte` gains a quiet "Hide" text link, revealed on hover, sitting next to (not inside) the existing `⋯` menu trigger — a sibling affordance, not a new menu item. Clicking it adds `entry.principal.id` to the exclusion set. Unlike the `⋯` menu, this link is unconditional: it does not depend on `editTargetForEntry`/`editingEnabled`, so it renders on `Member` rows and under a historical (non-latest) Comparison exactly as it does everywhere else — hiding is not an edit and carries none of ADR-0021/ADR-0022's editing-scope restrictions (resolves the former open Question 7: menu availability never gated hiding in the first place, since hiding was never part of that menu).
- **Managing exclusions — tree-top banner**: once ≥1 Principal is excluded, a slim banner appears above the Roster tree: "N principals hidden this session," plus a "Manage" toggle (reads "Hide list" while expanded) that reveals one row per excluded Principal with its own "Unhide," plus a bulk "Unhide all." The banner itself has zero footprint when nothing is excluded. There is no separate `FilterBar` popover, funnel icon, or multi-select/autocomplete control for *adding* exclusions — the row's "Hide" link is the only add path, which also makes the former open Question 2 (autocomplete data source) moot.
- **Proposed seam for new pure logic**: mirrors the existing pattern used for search — a new predicate (e.g. `isExcluded(entry, excludedIds)`) colocated in `rosterRow.ts` next to `matchesSearchQuery`, folded into `isEntryVisible` in `filterBar.ts` alongside the existing view-mode/search conditions. This keeps the single highest-value seam (the already-tested `filterBar.ts`/`rosterRow.ts` pure-function layer) rather than introducing a new module.

## Testing Decisions

- Follows the existing colocated-`*.test.ts` convention (ADR-0017): pure logic added to `rosterRow.ts`/`filterBar.ts` gets test cases added to the existing `rosterRow.test.ts`/`filterBar.test.ts` files, not a new test file.
- Test only external behavior of the new predicate(s) and the extended `isEntryVisible`/`visibleRepos`/`viewCounts`, not implementation details — prior art: the existing `matchesSearch`/`isSearchMatch`/`isEntryVisible` tests in `filterBar.test.ts` already cover the equivalent shape (blank input is a no-op, AND-combination with view mode, repo-disappears-at-zero-rows, count recompute).
- Key cases to cover once implementation starts: excluding a Group cascades to its Member rows but not an unrelated Direct grant on the same person (User Story 5); excluding a user hides all their entries across access types; a repo with only excluded rows drops out of `visibleRepos`; exclusion AND-composes correctly with an active search and with Changes-only mode simultaneously.
- Svelte component rendering (the row's hover-revealed "Hide" link, the tree-top banner and its Manage list) stays manual/`pnpm tauri dev`-verified per ADR-0017 — no Playwright, no component-level automated tests.

## Out of Scope

- Persisting exclusions across app restarts (explicitly rejected — Question 1, Answer A).
- Free-text/label-substring-based exclusion (explicitly rejected — Question 2, Answer B; this is the one place this feature deliberately does *not* mirror Principal search's matching behavior).
- A native right-click/contextmenu interaction (considered and rejected — Question 6 follow-up; hiding lives on the row's own hover-revealed "Hide" link instead).
- A `FilterBar` popover/funnel-icon for adding exclusions via multi-select or autocomplete (considered in an earlier draft of this ticket, superseded once the reference design — `.draft/Ledger Light.dc.html` — confirmed the actual interaction model: the row's "Hide" link is the only add path, and a tree-top banner is the only manage surface).
- Any change to how Principal search or the All access/Changes only view mode themselves behave — this feature only adds a third AND-ed condition, it doesn't touch the existing two.
- CSV Export honoring exclusions — Export stays a flat, unfiltered, diff-free roster regardless of on-screen filter state (ADR-0026), same treatment as view mode and search get today (resolves former open Question 3).
- Group membership as a diffable entity (pre-existing non-goal, unrelated to and unaffected by this feature).

### Design notes

#### How it works (the trigger):

Hovering any row in the tree reveals a quiet "Hide" text link next to the existing ⋯ menu (which still holds level-change/remove-access actions, and is otherwise unaffected).

Click it and that principal's rows disappear from the tree immediately — matched by their stable identity (account/group ID), not the displayed label, so the same principal is suppressed everywhere it appears across repos, and renames don't break it. The link renders unconditionally, independent of whether the `⋯` menu itself is present for that row (`Member` rows, historical Comparisons).

#### How it's tracked (the banner):

A slim banner appears at the top of the tree only when ≥1 principal is hidden: "N principals hidden this session."
"Manage" expands it into a list of the hidden principals, each with its own "Unhide," plus "Unhide all" to fully reset. There is no other surface for adding or managing exclusions.

Design intent: minimal new surface (reuses the row's existing action affordance), zero cost when unused (banner only appears once something's hidden), and always reversible/visible so a hidden principal is never silently forgotten.
