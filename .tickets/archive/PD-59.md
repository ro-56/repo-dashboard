## Problem Statement

When an auditor spots an unwanted or over-provisioned grant in the roster/diff dashboard — say, an escalation surfaced by the Comparison view — there's currently nothing they can do about it inside repo-dashboard. They have to leave the app, find the same repo or project in Bitbucket's own web UI, locate the same user or group by hand, change or remove the permission there, and then come back and re-run to confirm it landed. That's slow, and the round-trip through a second UI is exactly where mistakes creep in (wrong repo, wrong user, wrong level).

## Solution

Add an edit control directly to Direct and Group grant rows in the roster (both Repo-level and Project-level), matching the finalized reference design (`.references/new-design/Ledger Light.dc.html` / `Ledger Dark.dc.html`). Opening a row's menu lets the auditor set a new Read/Write/Admin level or remove the grant entirely. Edits accumulate as local **Pending edits** — nothing touches Bitbucket yet — across as many rows and repos/projects as the auditor wants. A single global **Apply** action reviews every staged change (with cascade counts for Group removals, since those also drop every Member grant derived from them) in a confirm dialog, then commits the whole batch to Bitbucket in one action. Afterward, the auditor is prompted to re-run to see the change land in a fresh Snapshot, since Snapshots are immutable and never self-update.

## User Stories

1. As an auditor, I want to change a Direct grant's level on a repo, so that I can correct an over-provisioned permission without leaving the dashboard.
2. As an auditor, I want to remove a Direct grant on a repo entirely, so that I can revoke access I've identified as unwanted.
3. As an auditor, I want to change a Group grant's level on a repo, so that every member inheriting from that group is corrected in one action instead of editing each member individually.
4. As an auditor, I want to remove a Group grant on a repo entirely, so that I can revoke that group's access to the repo.
5. As an auditor, I want to change a Direct grant's level at the Project level, so the fix cascades to every repo the project owns instead of repeating it per repo.
6. As an auditor, I want to remove a Direct grant at the Project level, so cascading access is fully revoked in one action.
7. As an auditor, I want to change a Group grant's level at the Project level, so the fix cascades to every repo the project owns.
8. As an auditor, I want to remove a Group grant at the Project level, so the removal cascades to every repo the project owns.
9. As an auditor, I want Member rows to have no edit control at all, so I'm never misled into thinking I can directly change a permission that's actually derived from a group.
10. As an auditor, when I open the menu on a Group grant I'm about to remove, I want to see how many Member grants derive from it, so I understand the full blast radius before I stage the removal.
11. As an auditor, when I open the menu on any Project-level grant, I want to see the existing "applies to all N repos" cascade note, so I understand the scope of the change I'm about to stage, consistent with how that note already reads elsewhere in the dashboard.
12. As an auditor, I want my in-progress edits clearly marked "pending" on their row, so I can tell staged-but-unapplied changes apart from the actual current state.
13. As an auditor, I want to undo a staged edit before applying it, so a misclick costs me nothing.
14. As an auditor, I want a single global count of how many edits are staged, so I know how much I've queued up before committing anything.
15. As an auditor, I want a confirmation step listing every staged change before anything is sent to Bitbucket, so I get one last chance to catch a mistake across a whole batch.
16. As an auditor, I want to cancel out of the confirmation dialog without applying anything, so reviewing the batch doesn't force my hand.
17. As an auditor, I want editing controls enabled only while I'm viewing the latest Snapshot as the Comparison, so I never mutate live Bitbucket state while looking at a stale historical view.
18. As an auditor, if I've staged edits and a new Run then completes, I want those now-stale edits cleared rather than silently carried forward, so I never act on a decision made against out-of-date data.
19. As an auditor, when a batch partially fails (say, one grant was already changed by someone else and now 404s), I want every other staged change to still go through, so one bad item doesn't block everything else I confirmed.
20. As an auditor, I want per-item results after applying a batch — which succeeded, which failed and why — so I know exactly what to retry or investigate.
21. As an auditor, I want failed items to remain staged after a partial-failure apply, so I can retry or discard them without redoing the whole batch.
22. As an auditor, after a successful apply, I want to be told to re-run to see the change reflected, so I understand the dashboard won't update itself outside the Snapshot model.
23. As an auditor whose credential lacks the right Bitbucket scope, I want a clear per-item error when my apply fails for that reason, so I understand it's a scope problem, not a broken feature.
24. As an auditor, I want the level picker to only ever offer Read/Write/Admin, so I'm never offered a level the rest of this tool can't display or diff.
25. As an auditor, I want adding a brand-new grant for a principal with zero current access to be out of reach in this feature, so its scope stays predictable and matches the reference design exactly.

## Implementation Decisions

- **`BitbucketClient` trait** (`src-tauri/src/client.rs`) gains write methods mirroring the shape of its existing read methods: set/remove a Direct grant and set/remove a Group grant, each at Repo scope and at Project scope (8 methods total). These map 1:1 onto Bitbucket's real endpoints, confirmed against `developer.atlassian.com/cloud/bitbucket/rest`:
  - Repo scope: `PUT`/`DELETE /2.0/repositories/{workspace}/{repo_slug}/permissions-config/users/{selected_user_id}` and `.../permissions-config/groups/{group_slug}` — requires `repository:admin` scope.
  - Project scope: `PUT`/`DELETE /2.0/workspaces/{workspace}/projects/{project_key}/permissions-config/users/{selected_user_id}` and `.../permissions-config/groups/{group_slug}` — requires `project:admin` scope.
  - `RealBitbucketClient` is the only implementation making real network calls, same as today.
- **New pure Rust module** with a single entry point, e.g. `apply_pending_edits(client: &impl BitbucketClient, workspace: &str, edits: Vec<PendingEditRequest>) -> Vec<ApplyResult>`. Each `PendingEditRequest` carries a `GrantScope`, a target (`Direct(account_id)` or `Group(group_slug)`), `repo_project`/`repo`, and either `SetLevel(Permission)` or `Remove`. Each edit is routed to the matching trait method and applied independently — no early abort on failure (ADR-0022, `docs/adr/0022-permission-edits-staged-batch-apply.md`). `ApplyResult` reports per-item success or a typed error mirroring `ClientError` (`Unauthorized` / `RateLimited` / `Other`).
- **Thin Tauri command** (`apply_pending_edits`), following the existing `lib.rs` convention (see `run_now`, `delete_snapshot`): wires managed credential/workspace state to the pure function and stringifies errors for the frontend. No new persisted state — `PermissionRecord`/`Snapshot` schema is unchanged; edits are never stored, only mutate live Bitbucket and are reflected in the dashboard on the next Run.
- **Frontend — `pendingEdits.ts`** (new pure TS module): holds the Pending-edit state (stage a level-change or removal keyed by scope+principal+repo/project, undo one, clear all) and derives the confirm dialog's view model (repo/project, principal, source, scope, before → after or removal, cascade note/count) from current pending state plus the roster tree.
- **`rosterRow.ts`** gains menu-building functions: level options (highlighting the current effective level) and a remove action, for Direct and Group entries only — Member entries get no menu. Group-row menus additionally surface a cascade count computed from how many Member entries in the roster tree derive from that group at that repo/project; Project-scope rows reuse the existing cascade-note text already shown elsewhere in the dashboard.
- **Global Apply control**: lives in the head bar area, shows the count of staged edits, enabled only when count > 0 and the Comparison is the latest Snapshot (ADR-0022). Selecting a non-latest Comparison, or a new Run completing, clears all Pending edits via `pendingEdits`'s clear.
- **Confirm dialog**: lists every staged change before Confirm invokes the `apply_pending_edits` Tauri command; Cancel discards nothing (edits remain staged). After apply, a results view shows per-item success/failure and prompts the user to re-run; failed items remain staged for retry.
- Credential scope is never proactively probed (ADR-0023) — insufficient scope only surfaces as a per-item `Unauthorized` result during Apply, handled through the same per-item error path as any other failure.

## Testing Decisions

- Good tests here assert externally observable behavior — which fake-client methods were called, with what arguments, and what `ApplyResult`s came back — never internal control flow. This mirrors the existing `FakeClient` pattern already proven in `collect.rs`'s test suite (call-count tracking, canned `Ok`/`Err` responses keyed by repo/group/project).
- **Rust (`cargo test` in `src-tauri`)**: `apply_pending_edits` tests cover routing a Direct-repo level edit to the right client method, a Direct-repo removal, and the Group/Project equivalents (8 routing combinations); a batch where one item fails still applies and reports the rest; `Unauthorized`/`RateLimited`/`Other` client errors surface distinctly per item.
- **Frontend (`vitest`)**: colocated `pendingEdits.test.ts` covering stage/undo/clear semantics and confirm-view derivation (including cascade counts); colocated additions to `rosterRow.test.ts` covering that Direct/Group entries get a menu and Member entries don't, level options reflect the current effective level, and the Project-scope cascade note appears where expected. No Svelte component rendering tests (ADR-0017 defers those) — the confirm dialog markup, head-bar Apply button wiring, and edit-controls-disabled-on-non-latest-Comparison behavior are verified manually via `pnpm tauri dev`.

## Out of Scope

- Adding a brand-new grant for a principal with currently zero access (future ticket — the reference design has no "add" affordance).
- Modeling Bitbucket's `create-repo`/`none` project-level permission values anywhere in this feature (ADR-0021). This also does not fix the pre-existing crash when the *read* path encounters a `create-repo` grant during a Run — filed separately as **PD-58**.
- Editing Member grants directly — no Bitbucket resource backs an individual member's permission independent of their group (ADR-0021).
- Proactive credential-scope validation/probing (ADR-0023).
- Auto-triggering a new Run after a successful apply (ADR-0022) — the user re-runs manually.
- Per-card/per-repo Apply controls — only one global Apply exists (ADR-0022).
- Any changes to the Execution-history page (PRD §5.5), which remains separately un-designed.

## Further Notes

- Reference design (`.references/new-design/Ledger Light.dc.html` / `Ledger Dark.dc.html`) shows the row menu, level options, "pending · unsaved" tag, and per-row undo, but has **no visible Apply control anywhere in the file** — this spec deliberately adds that missing piece (ADR-0022) rather than treating the mockup as complete as-is.
- This session produced three new ADRs — `docs/adr/0021-permission-editing-scope-boundaries.md`, `0022-permission-edits-staged-batch-apply.md`, `0023-credential-scope-checked-lazily.md` — and new `CONTEXT.md` glossary entries (`Pending edit`, `Apply`, `Remove grant`), plus an amendment to the existing `Member grant` entry noting its non-editability.
- `PermissionRecord`'s identity fields (`Principal.id` = Bitbucket `account_id` for users, group slug for groups; `repo_project` = Bitbucket project key) already carry everything needed to target the write endpoints — no schema changes required there.
## Notes

Live editing of Direct/Group permission grants delivered as three tracer-bullet tickets: PD-60 (Direct/Repo), PD-61 (Direct/Project), PD-62 (Group/both scopes with cascade-count warning). BitbucketClient gained 8 write methods (set/remove x Direct/Group x Repo/Project) mapping 1:1 onto Bitbucket's permissions-config endpoints; apply_pending_edits exhaustively routes all (scope, target) combinations, each item applied independently per ADR-0022. Frontend: pendingEdits.ts holds staged edits, rosterRow.ts builds the Read/Write/Admin+Remove menu for Direct/Group entries at either scope (Member rows permanently menu-less per ADR-0021), a global Apply control and confirm dialog in the head bar gate on the Comparison being the latest Snapshot and clear on a new Run. Cascade counts for Group removals are computed once and reused identically in both the row menu and confirm dialog. GUI walkthroughs via pnpm tauri dev were not performed across all three tickets — sandboxed dev environment has no display.
