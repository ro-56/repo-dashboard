## What to build

Extends Refresh (PD-68) to handle Project-scope targets. A Project-scope successful edit now also contributes a target: the core Refresh function refetches that Project's Direct+Group permissions once (live membership resolution, as with repo targets) and cascades the result to every repo the *source Snapshot* already records under that Project's key — never a fresh repo-discovery call to redetermine Project membership. The frontend restriction from the Repo-scope tracer bullet is removed: Refresh is now offered whenever a batch has at least one successful edit, regardless of scope mix.

This ticket also carries the precise group-membership-status filtering rule needed once both scopes are in play: since the group-membership-status table has no scope column, the set of group_ids to drop-and-replace for a given target must be derived from the *old permission records* being replaced (that target scope's Group-typed records), not by a blanket match on repo/project — otherwise an untouched dimension's membership status for a group with grants at both scopes on the same repo could be silently dropped.

## Acceptance criteria

- [ ] The core Refresh function also derives Project-scope targets from successful ApplyResults, deduplicated the same way repo targets are.
- [ ] A Project-scope target's fetch runs once per targeted Project (not once per repo under it) and its result is applied to every repo the source Snapshot already records under that project key.
- [ ] A single fetch-failed status is recorded for a targeted Project that fails (not duplicated per repo it owns), with zero Project-scope records for every repo under it; other targets in the batch still refresh.
- [ ] A 401 on a Project-scope target aborts the whole Refresh the same way it does for a repo-scope target.
- [ ] The group-membership-status filtering rule is scoped by group_id derived from the old records being replaced, not by a blanket repo/project match — verified with a scenario where the same group holds grants at both scopes on the same repo, and only the touched scope's status is affected.
- [ ] A mixed batch (a Repo-scope edit on one repo plus a Project-scope edit on an unrelated Project) refreshes both independently and correctly in one Refresh.
- [ ] A repo that is both a direct Repo-scope target and part of a targeted Project has both its Repo-scope and Project-scope data refreshed correctly.
- [ ] The frontend's Refresh-availability gating from the Repo-scope tracer bullet is removed: the action is enabled whenever the batch has at least one successful result, regardless of scope.
- [ ] Manually verified via the dev app run for a mixed-scope batch.
