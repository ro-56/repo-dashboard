## What to build

Once the backend (PD-64) can produce and diff `create-repo` grants correctly, the roster UI needs to display them distinctly — the whole point of not aliasing `create-repo` straight to `Admin` is so a user can see which of the two a principal actually holds. Per ADR-0024 and the PD-63 spec: `create-repo` is visually admin-tier (sorts and styles alongside Admin), but its label text stays its own.

## Acceptance criteria

- [ ] The frontend's permission type includes `create-repo` as a recognized value.
- [ ] Roster row sort ordering places a `create-repo` grant at the same rank as `Admin`.
- [ ] Roster row styling (level class) renders a `create-repo` grant identically to an `Admin` grant.
- [ ] The row's displayed label text reads `create-repo` (hyphenated), not a raw lowercase of the wire value and not `admin`.
- [ ] The escalation tag ("escalation → admin") fires for an escalation into `create-repo`, the same as for an escalation into `Admin`.
- [ ] Existing colocated frontend tests for row derivation/sorting cover all of the above.
- [ ] Manually verified in `pnpm tauri dev` against a run containing a `create-repo` grant: the row displays and sorts correctly.

## Out of scope

- Giving `create-repo` its own segment in the repo card's distribution bar (ADR-0008) — separate future ticket per ADR-0024.
