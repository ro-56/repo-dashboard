## Problem Statement

Right now every string in repo-dashboard's UI is hardcoded English, authored inline in Svelte components and TS modules. The app is distributed as a single-user, single-workspace local install, but the people running those installs aren't all English speakers — someone whose preferred language isn't English has to read the whole permissions-audit dashboard (labels, tooltips, error messages, domain vocabulary like Grant/Revoke/Escalation) in a language that isn't their own, with no way to change that.

## Solution

Add a Display language setting to the dashboard: auto-detected from the OS/webview locale on first launch, overridable at any time via a picker in AppearancePanel (next to the existing Theme toggle), persisted the same way Theme already is. All app-authored UI strings — including the domain vocabulary defined in CONTEXT.md — render in the selected Display language via a `svelte-i18n` catalog, starting with English and Brazilian Portuguese. Content that doesn't belong to the app (Bitbucket-sourced repo/Project/Principal names, ISO dates, the CSV Roster export, and backend-originated error messages) stays fixed regardless of Display language, so audit dates and exported files remain unambiguous and comparable across installs.

## User Stories

1. As a non-English-speaking user running my own install, I want the dashboard's UI in my own language, so that I can read the permissions audit without translating it in my head.
2. As a first-time user, I want the app to guess my language from my OS settings, so that I don't have to configure anything before the UI is usable.
3. As a user whose OS locale doesn't match my preference (or isn't supported yet), I want to explicitly pick a different Display language in the AppearancePanel, so that auto-detection never traps me in the wrong language.
4. As a returning user, I want my explicit Display language choice to persist across app restarts and to never be silently overridden by a later OS-locale change, so that my choice sticks the same way my Theme choice already does.
5. As a pt-BR user, I want every domain term — Grant, Revoke, Escalation, Demotion, Level change, Direct/Group/Member grant, Baseline/Comparison, Snapshot, Run, Refresh, Pending edit, Apply — translated into precise Portuguese, so that I'm not forced to learn English audit vocabulary to use a tool in my own language.
6. As a pt-BR user, I want every tooltip, column header, count badge, row tag, and repo tag (the strings drafted in the recent tooltip-copy work) translated too, so that hover help is as usable as the rest of the UI.
7. As any user, I want repo names, Project names, and Principal (user/group) labels to always display exactly as Bitbucket returns them, regardless of my Display language, so that I'm never looking at a garbled or reinterpreted version of my own workspace's real names.
8. As any user, I want Snapshot/Run dates to always render as unambiguous ISO `YYYY-MM-DD`, regardless of Display language, so that comparing Runs never depends on guessing whether a date is day-first or month-first.
9. As any user, I want the CSV Roster export to always be in English, so that a file I hand to a reviewer or archive is parseable and consistent no matter what language my own install is set to.
10. As any user, I want to understand that backend-originated error messages (e.g. "could not reach Bitbucket", "could not save run") currently stay in English regardless of my Display language, so that I'm not confused when one error message looks untranslated while the rest of the UI is in my language.
11. As a pt-BR user encountering a brand-new feature whose strings haven't been translated yet, I want the UI to silently fall back to the English string for just that gap, so that one missing translation doesn't break or blank out the rest of the screen.
12. As a developer adding a new feature, I want a clear place to add new translation keys and a test that catches when a locale's catalog drifts out of sync with the English source of truth, so that missing translations are caught before they ship silently.

## Implementation Decisions

- **Library**: adopt `svelte-i18n` as a new runtime dependency (ADR-0028) — the app's first i18n dependency, a deliberate exception to the otherwise lean-dependency stance established by ADR-0017.
- **Catalogs**: one JSON (or TS) message catalog per supported language, keyed by a stable string id. English is the source-of-truth catalog; Brazilian Portuguese (`pt-BR`) is the second language shipped at launch. Every existing hardcoded UI string — including the strings introduced by the recent tooltip-copy work (row sigils, row meter, repo bar-cell, row tags, repo tags, count badges, column headers) — gets extracted into these catalogs rather than reworked in place.
- **Domain vocabulary is translated, not fixed**: CONTEXT.md's canonical terms (Grant, Revoke, Escalation, Demotion, Level change, Direct/Group/Member grant, Baseline/Comparison, Snapshot, Run, Refresh, Pending edit, Apply, etc.) name the *concept*; each language's catalog supplies its own precise word for that concept. This is now documented as the "Display language" term in CONTEXT.md.
- **Language selection module** (`language.ts` or equivalent): mirrors the existing `theme.ts` shape exactly — `getLanguage()`, `setLanguage(lang)`, `initLanguage()`. On init, reads an explicit stored choice from `localStorage` first; only when nothing is stored does it fall back to a one-time read of the OS/webview locale (`navigator.language`, or `@tauri-apps/plugin-os`'s `locale()` if `navigator.language` proves unreliable in the Tauri webview) to pick the closest supported language. An explicit stored choice always wins and is never overridden by a later OS-locale change — same invariant as Theme.
- **UI entry points**: `initLanguage()` is called once from `+layout.svelte` alongside the existing `initTheme()` call. A language picker is added to `AppearancePanel.svelte`, next to the existing Light/Dark segmented control, following the same pattern (`getLanguage()`/`setLanguage()` wired to local component state).
- **Persistence**: same mechanism as Theme — a dedicated `localStorage` key (e.g. `"language"`), storing a language tag (e.g. `"en"`, `"pt-BR"`).
- **Missing-translation fallback**: silent fallback to the English catalog string for any key missing from a non-English locale, using `svelte-i18n`'s built-in fallback-locale behavior. No visible "missing translation" marker is shown in the shipped build.
- **Scope boundaries** (each documented as its own ADR):
  - Bitbucket-sourced content (repo names, Project names, Principal labels) is passed through verbatim, never translated or transliterated — it isn't this app's content.
  - Dates always render as ISO `YYYY-MM-DD`, never locale-formatted via `Intl.DateTimeFormat` — unambiguous comparison across installs matters more than idiomatic per-locale formatting (no change to `headBar.ts`'s existing `formatDate`).
  - Backend (Rust) error strings (`RunError`, `DeleteSnapshotError`, `RefreshError` in `src-tauri/src/lib.rs`) stay English-only for now (ADR-0029) — translation is owned entirely by the frontend `svelte-i18n` catalog; Rust doesn't get a parallel translation mechanism in this pass.
  - The CSV Roster export (ADR-0026) always renders its column headers and content in English regardless of the exporting user's Display language (ADR-0030) — it's a fixed, parseable export schema, not a personalized view.

## Testing Decisions

- Tests should verify observable behavior (what a caller of the module sees), not internal implementation — consistent with this repo's existing colocated-`*.test.ts` convention (ADR-0017) and the code style already used in `theme.test.ts`.
- **`language.ts` test** (new, colocated `language.test.ts`): directly mirrors `theme.test.ts`'s structure and even its stubbing helpers (`fakeStorage`, `stubEnv`-style globals for `localStorage`/OS-locale source). Cases: an explicit stored choice is read and applied without consulting OS locale; an explicit stored choice is never overridden by a later OS-locale change; falls back to the OS-detected language when nothing is stored and that language is supported; falls back to English when nothing is stored and the OS locale isn't a supported language; `setLanguage` persists the choice and updates the active catalog.
- **Catalog key-parity test** (new): asserts every non-English locale catalog (starting with `pt-BR`) has exactly the same set of keys as the English source-of-truth catalog — no missing keys, no stale/orphaned keys left over from removed strings. This is the only automated backstop against the silent-English-fallback behavior masking real gaps as new features land.
- Component-level string swaps (RepoCard, RosterRow, CountBadges, RosterColumnLabels, HeadBar, FilterBar, SideDrawer, RunPanel, SnapshotsPanel, CredentialsPanel, ConfirmApplyDialog, AppearancePanel, EmptyState) are not independently unit-tested — Svelte component rendering tests remain deferred per ADR-0017. These are verified manually via `pnpm tauri dev`, switching Display language and checking each screen.

## Out of Scope

- Locale-aware number/date/currency formatting (`Intl.DateTimeFormat`/`Intl.NumberFormat`) — dates stay fixed ISO `YYYY-MM-DD`; there are no other formatted numbers/currency in this app today.
- Translating or transliterating Bitbucket-sourced data (repo names, Project names, Principal labels).
- Translating the CSV Roster export.
- Translating backend (Rust) error strings — deferred to a future pass if needed (ADR-0029).
- Any languages beyond English and Brazilian Portuguese at launch.
- Multi-user or per-user language preferences — this remains a single-user, single-workspace install per the project's non-goals; Display language is a single, install-wide setting like Theme.
- Svelte component rendering tests / Playwright E2E coverage of the localized UI — deferred per ADR-0017, unaffected by this feature.
- A visible "missing translation" marker/dev-mode warning UI.

## Further Notes

- Three ADRs were written during design and should be read before implementation: ADR-0028 (svelte-i18n adopted despite the lean-dependency stance), ADR-0029 (backend errors excluded from localization), ADR-0030 (CSV export always English, extending ADR-0026).
- `CONTEXT.md` gained a new "Display language" glossary term tying these boundaries together — read it before touching any of the scope-boundary behavior above.
- The recently-finished tooltip-copy work (`tooltip-copy-draft.md` and its corresponding component/module changes) is the first real content to run through the extraction process — it's a good first test of whether the key-naming convention and extraction workflow are usable, before the rest of the app's strings are migrated.
