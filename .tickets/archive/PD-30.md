## What to build

Surface Grant scope and Project fetch status in the roster query layer, so the dashboard's data source reflects Project-level grants and Project-level fetch failures per repo.

- `build_roster_tree`/`get_roster_tree` extended so every grant row in the tree carries its `scope` (Repo or Project).
- Each repo's entry in the tree is joined with its owning Project's `ProjectFetchStatus` at query time (loaded fresh per request, consistent with the existing no-caching/no-materialization approach for the Roster tree, per ADR-0004).
- A repo whose own fetch succeeded but whose Project's fetch failed shows its own data fully, plus an indication that the Project layer is unknown for that repo.

## Acceptance criteria

- [ ] A repo with both Repo-level and Project-level grants for the same principal shows both as separate rows in the roster tree, each labeled with its scope.
- [ ] A `ProjectFetchStatus::FetchFailed` for a project appears against every repo belonging to that project in the tree output.
- [ ] A repo's own `RepoStatus` is unaffected by its project's `ProjectFetchStatus` — a repo can be `Ok` at the repo level while its project shows `FetchFailed`.
- [ ] Diff markers (Grant/Revoke/Escalation/Demotion) computed for Project-level rows behave identically to Repo-level rows in the tree output.
- [ ] Tests follow the existing `roster.rs` test pattern (hand-built or storage-loaded Snapshot fixtures); no HTTP involved.
## Notes

Extended roster.rs: PrincipalEntry now carries scope (Repo/Project), and RepoNode joins ProjectFetchStatus per repo at query time via project_key==repo_project, independent of the repo's own RepoStatus. 6 new tests cover separate rows for same-principal Repo+Project grants, project fetch failure fan-out, and Grant/Revoke/Escalation/Demotion parity for Project-scoped rows.
