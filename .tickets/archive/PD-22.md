## What to build

Replace `credentials.rs`'s in-memory `Mutex<Option<Credentials>>` with real OS-keychain-backed persistence (e.g. the `keyring` crate), so credentials survive an app restart. This closes the gap PD-5 deliberately left open (see the comment at the top of `credentials.rs`) and satisfies PRD §5.1 ("stored locally, encrypted at rest ... via OS keychain").

Add a `get_credentials` command that reports whether credentials are set and returns username/workspace (never the app password) — needed by later tickets to render a "connected as X" state instead of a blank form.

Backend-only slice. No UI changes required; verify via `cargo test`.

## Acceptance criteria

- [ ] `set_credentials` writes username/app_password/workspace to the OS keychain instead of an in-memory `Mutex`
- [ ] `run_now` reads credentials from the keychain rather than from in-process state
- [ ] Credentials persist across an app restart (keychain-backed, not process memory)
- [ ] New `get_credentials` command returns `{ username, workspace, hasCredentials: bool }` — never the app password
- [ ] `cargo test` covers: set → restart (simulated) → get round-trip; get when nothing is set
- [ ] No plaintext file fallback introduced anywhere
## Notes

Replaced the in-memory Mutex<Option<Credentials>> with a keyring_core-backed CredentialsStore: production uses the platform-native keychain (apple/windows/zbus-secret-service), lazily initialized on first set/get so a missing OS keychain service surfaces as a command error instead of panicking at startup. Added get_credentials returning {username, workspace, hasCredentials} (never the app password). run_now now reads credentials from the keychain. cargo test covers set->restart(simulated)->get round-trip and get-with-nothing-set against an in-memory keyring_core::mock::Store, so tests never touch a real OS keychain.
