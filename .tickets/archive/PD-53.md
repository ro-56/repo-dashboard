## Problem Statement

On the roster grid, the `.source` cell — the grant-source column, which ADR-0006 establishes as row identity, not decoration — currently marks a Project-level grant (ADR-0012's Grant scope) by appending a literal `" · project"` text suffix to the base source label (ADR-0014: `direct` → `direct · project`, `grp:secops` → `grp:secops · project`). Combined with a group-derived label, this can produce strings up to ~21 characters wide inside a fixed 104px column that, per ADR-0009, must never shed under responsive reflow — it's the last column standing at the 900px floor.

In practice this routinely truncates. The tooltip meant to back it up (`title={source}`) just echoes the same already-cut-off string, so the one attribute the suffix exists to preserve — Grant scope — is frequently the exact thing hidden from a workspace admin scanning the roster.

## Solution

Replace the text suffix with a compact, monochrome prefix glyph — `↳` (U+21B3, "downwards arrow with tail") — placed before the base source label whenever a grant is Project-scoped: `↳ direct`, `↳ grp:secops`. Repo-scoped grants (the common case) remain unmarked, unchanged from today's behavior.

The glyph is rendered in `.source`'s existing `--ink-3` color, carrying no independent hue of its own — required by ADR-0005, which reserves hue exclusively for diff state and mandates that any other state "express itself through tags or gutters," never a color of its own. It stays inside the `.source` cell rather than moving to the `.tags` column: Project-scope is a structural/identity fact, part of the same composite grant-source key as `AccessType` (ADR-0012), not an exceptional per-row state on the level of an escalation or an unresolved group — and because a single Project-level grant flattens into one row per cascaded repo (ADR-0012), Project-scoped rows can be the *majority* in a Project-heavy workspace, which would dilute `.tags`'s "something unusual here" signal if used there instead.

The `title` tooltip for Project-scoped rows is upgraded from truncation insurance (echoing the same short text back) into a short explanatory string: `"↳ Project-level grant"`. Repo-scoped rows keep their current tooltip behavior — nothing new to explain.

## User Stories

1. As a workspace admin scanning the roster, I want a Project-level grant to stay visually distinguishable from a Repo-level one even in a narrow column, so that I don't mistake a cascading grant for a one-off repo-specific grant.
2. As a workspace admin auditing a group-derived permission (`grp:secops`), I want the Project-scope indicator to still be visible even when combined with a longer group-name label, so that neither piece of identity information gets silently dropped to truncation.
3. As a workspace admin resizing the app window down toward the 900px floor, I want the Project-scope marker to survive exactly as reliably as the rest of the source column (ADR-0009: the source column never sheds), so that scope information doesn't degrade differently from the rest of row identity under reflow.
4. As a workspace admin unfamiliar with the `↳` glyph on first use, I want to hover it and get a short, plain-language explanation ("Project-level grant"), so that I don't have to guess what the symbol means or consult external documentation.
5. As a workspace admin, I want the Project-scope indicator to never compete visually with diff-state color coding (added/revoked/changed/escalation), so that an escalation audit signal is never diluted by an unrelated visual channel.
6. As a workspace admin scanning a Project-heavy workspace where most rows are Project-scoped, I want the scope indicator to live in the source cell rather than as a tag, so that the `.tags` column keeps working as a signal for genuinely exceptional per-row states (escalation, unresolved membership) rather than being flooded by a routine marker.
7. As a workspace admin viewing a Repo-scoped grant (the common case), I want the source cell to render exactly as it does today (no prefix, no visual change), so that the common case isn't burdened with new visual noise for a distinction that doesn't apply to it.
8. As a developer maintaining the roster grid's CSS, I want the Project-scope glyph to render using a Unicode codepoint with broad font coverage (the general Arrows block, not Miscellaneous Symbols and Arrows), so that the glyph doesn't silently fall back to a mismatched system font next to `IBM Plex Mono` text.
9. As a developer reading the codebase later, I want ADR-0014 marked superseded and a new ADR recorded explaining why the suffix became a glyph, so that a future reader doesn't "fix" the glyph back into a text suffix without understanding the truncation problem it solves.

## Implementation Decisions

- **Module touched**: `src/lib/rosterRow.ts`, specifically the `sourceLabel` function (currently `sourceLabel(accessType: AccessType, scope: GrantScope): string`, ADR-0014). Its behavior changes from appending a trailing `" · project"` string to prepending a `"↳ "` prefix when `scope === "Project"`. Repo-scoped output is unchanged.
- **Tooltip threading**: today `RosterRow.svelte` sets `title={source}` — the same string shown in the cell, purely as truncation insurance. That no longer makes sense once the visible text no longer truncates away the scope signal. The module needs to expose enough for the component to render a *different* string for `title` than for the visible label — either by returning a `{ label, title }` shape from `sourceLabel`, or via a second small pure function (e.g. `sourceTooltip(accessType, scope)`). Exact shape is left to implementation, but it must remain a pure, colocated-testable function per this module's existing pattern (`isUnresolvedGroup`, `hasDiff`, `deriveRow`, etc.) — no logic moves into the `.svelte` file itself.
- **Glyph**: `↳` (U+21B3, "DOWNWARDS ARROW WITH TAIL"), chosen over `⤷` (U+2934, "Miscellaneous Symbols and Arrows" block) specifically for broader font coverage — U+21B3 sits in the core Arrows block (U+2190–21FF), more likely to be covered by `IBM Plex Mono` (`--font-mono`) or a visually consistent fallback than a glyph from the miscellaneous-symbols block.
- **Color**: no new CSS custom property. The glyph inherits `.source`'s existing `color: var(--ink-3)` — deliberately no independent hue, per ADR-0005.
- **Placement**: prefix, not suffix — `↳ direct`, `↳ grp:secops`. A single space between glyph and label.
- **Scope of the change**: only the Project-scope branch of `sourceLabel`'s output changes. Repo-scope output, `compareEntries`'s `SOURCE_RANK` tie-breaking, and every other function in `rosterRow.ts` are untouched — this is not a broader refactor of the source column.
- **Documentation**: write a new ADR (next sequential number after the current highest in `docs/adr/`) recording this decision, and set ADR-0014's status to `superseded by ADR-00NN`. The new ADR should capture: the truncation problem observed in practice, the ADR-0005 hue constraint that ruled out a colored emoji, the `.tags`-frequency argument for keeping scope in `.source` rather than moving it to `.tags`, and the U+21B3-over-U+2934 font-coverage reasoning. No `CONTEXT.md` changes are expected — "Grant scope" is already a defined term, and this decision is purely about its visual encoding, which is an implementation detail out of scope for the glossary.

## Testing Decisions

- **Seam**: `src/lib/rosterRow.ts`'s colocated `rosterRow.test.ts` (vitest), the same seam already covering `sourceLabel`, `compareEntries`, and `deriveRow`. This matches ADR-0017's commitment to test frontend pure-TS logic modules incrementally at the point a ticket touches them, and is the highest/only seam this change needs — no new seam is introduced.
- **What changes in the existing suite**: the current `sourceLabel` test cases (`rosterRow.test.ts`) assert the old `` `${label} · project` `` suffix format for all three `AccessType` variants (`Direct`, `Group`, `Member`) at `Project` scope, and assert no suffix at `Repo` scope. These must be updated to assert the new `` `↳ ${label}` `` prefix format instead, keeping the existing "Repo scope has no marker" cases as-is.
- **New coverage needed**: whatever mechanism carries the tooltip text (a `{label, title}` return shape, or a second function) needs its own test cases — asserting the explanatory `"↳ Project-level grant"` string appears only for Project-scoped entries, and that Repo-scoped entries' tooltip behavior is unchanged from today.
- **What a good test here looks like**: assert on the returned string(s) for each `AccessType` × `GrantScope` combination (external behavior of the pure function), not on implementation details like which internal branch was taken. This matches the existing `it.each(cases)` pattern already used for `sourceLabel` in this file.
- **Not covered by automated tests**: actual glyph rendering (font fallback behavior, visual alignment, whether `↳` looks right next to `IBM Plex Mono` text) is a Svelte-component/CSS concern, deferred per ADR-0017 — verified manually via `pnpm tauri dev`, not vitest.

## Out of Scope

- Any change to Repo-scoped rendering — it stays exactly as it is today (no prefix, no marker).
- Any change to `compareEntries`'s sort/tie-break logic — scope does not currently participate in row ordering, and this spec doesn't add it.
- Moving scope into a dedicated eighth roster column, or widening `--roster-cols`'s 104px `.source` track — explicitly rejected by ADR-0014 and not reopened here.
- Any change to how `.tags` renders or what qualifies as a tag (escalation, unresolved membership) — this spec keeps scope out of `.tags` entirely.
- Adding a visible marker for Repo scope (the common case) for symmetry with the new Project-scope glyph — Repo scope stays implicit/unmarked, matching ADR-0014's original framing of it as the default case.
- Accessibility beyond the `title` tooltip (e.g. dedicated screen-reader labeling, ARIA attributes) — not raised as a requirement in this cycle and not addressed here.
- Any CSV/export representation of the source label — the project has no export feature (PRD non-goals).

## Further Notes

This spec supersedes ADR-0014's suffix approach but keeps its core structural decisions intact: scope still rides in the existing `.source` cell rather than claiming new horizontal space, and Repo-scope is still the unmarked default. The change is narrowly about *how* Project-scope is encoded (glyph vs. text) in response to an in-practice truncation problem, not a re-litigation of *where* it lives.

The exact return shape for threading the tooltip string out of `rosterRow.ts` (single object vs. two functions) is an implementation detail left open deliberately — whichever keeps the module's existing "pure functions only, markup lives in `.svelte`" convention (see the file's header comment) intact.
