## What to build

Wire real Project-level permission fetching into the "Run now" pipeline, so every Run collects each distinct Project's Direct/Group/Member grants exactly once and reflects them on every repo that Project owns.

- `BitbucketClient` trait gains `list_project_direct_permissions(workspace, project_key)` and `list_project_group_permissions(workspace, project_key)`, implemented in `RealBitbucketClient` against Bitbucket's `/workspaces/{workspace}/projects/{project_key}/permissions-config/{users,groups}` endpoints, reusing the same pagination/retry/error handling as the existing repo-level methods.
- `collect_and_store` fetches each distinct `project_key` at most once per Run (caching results the same way group membership is already cached per Run), feeds the raw responses through Ticket 1's `normalize_project_*` functions, and flattens the resulting records onto every repo belonging to that project.
- A Project-level `Unauthorized` response aborts the whole Run, same as today's repo/group handling; `RateLimited`/`Other` marks that project's `ProjectFetchStatus::FetchFailed` and the Run continues, independent of the `RepoStatus` of any repo in that project.
- `ProjectFetchStatus` is persisted via `save_snapshot` alongside the rest of the Snapshot's data.

## Acceptance criteria

- [ ] `FakeBitbucketClient` (in `collect.rs`'s test module) extended with project-permission and project-group-permission fixtures.
- [ ] A project shared by multiple repos in the same Run has its permissions fetched exactly once (asserted via a call-count fake, same pattern as the existing `group_members_call_count`).
- [ ] Every repo belonging to a project ends up with that project's Direct/Group/Member grants as `scope: Project` records after a Run.
- [ ] A project-level fetch failure produces `ProjectFetchStatus::FetchFailed` for that project only; other projects' data and every repo's own `RepoStatus` are unaffected.
- [ ] `Unauthorized` on either new client call aborts the whole Run with no Snapshot written, same as existing repo/group `Unauthorized` handling.
- [ ] A full Run against `FakeBitbucketClient` with a mix of projects (some healthy, one failing) persists correctly and is verifiable via `load_snapshot`.
- [ ] No changes to the roster query layer or any Tauri command signature beyond what's already needed to persist the new data.
