## What to build

Add Grant scope (Repo vs Project) as a new dimension to the permission model, and extend normalization, diffing, and storage to carry it — with no HTTP or Tauri wiring yet. This is the pure-logic tracer bullet that proves the record shape and diff/storage semantics before anything calls the real Bitbucket Project endpoints.

- New `GrantScope` enum (`Repo` | `Project`) added as a field on `PermissionRecord`, orthogonal to the existing `AccessType` (`Direct`/`Group`/`Member`), per ADR-0012.
- New `normalize_project_permissions` and `normalize_project_group_permissions` functions mirroring the existing `normalize_repo_permissions`/`normalize_repo_group_permissions`, tagging every produced record `scope: Project` (including Project-level Member grants, reusing the existing group-membership-resolution logic and `GroupMembershipStatus` tracking unmodified).
- Existing `normalize_repo_permissions`/`normalize_repo_group_permissions` updated to tag their output `scope: Repo`.
- `diff.rs`'s `RecordKey` extended from `(repo, principal_id, AccessType)` to `(repo, principal_id, GrantScope, AccessType)`.
- New `ProjectFetchStatus` type (mirrors `RepoFetchStatus`): per-`project_key`, per-Snapshot fetch outcome (`Ok` | `FetchFailed`).
- `storage.rs`: `encode_access_type`/`decode_access_type` extended to persist/load `scope`; new table + save/load functions for `ProjectFetchStatus`.

## Acceptance criteria

- [ ] `GrantScope` enum exists with `Repo` and `Project` variants; `PermissionRecord` carries a `scope` field.
- [ ] `normalize_project_permissions` produces `PermissionRecord`s with `access_type: Direct`, `scope: Project` from a project's raw user-permissions response.
- [ ] `normalize_project_group_permissions` produces `Group` and (when membership is resolvable) `Member(group_id)` records, all `scope: Project`, plus the associated `GroupMembershipStatus`, from a project's raw group-permissions + members response.
- [ ] Existing repo-level normalize functions' output is unchanged except now explicitly `scope: Repo`.
- [ ] A Repo-level and a Project-level grant of the same `AccessType` and level, for the same principal + repo, diff as two independent records (Grant/Revoke each computed separately, never collapsed).
- [ ] A grant moving from `scope: Repo` to `scope: Project` (same principal, repo, `AccessType`, level) between two Snapshots diffs as a Revoke plus a Grant.
- [ ] `ProjectFetchStatus` round-trips through `save_snapshot`/`load_snapshot` (or equivalent) for a given `project_key` and Snapshot id.
- [ ] `scope` round-trips correctly for `Direct`, `Group`, and `Member(group_id)` records through the existing encode/decode storage functions.
- [ ] All new/changed logic covered by `cargo test`; no HTTP client or Tauri command changes included.
