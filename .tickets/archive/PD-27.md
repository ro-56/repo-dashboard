## Problem Statement

Bitbucket lets permissions be granted at the **Project** level, not just on individual repos — a user or group can be given Direct or Group access to a Project, and that access cascades to every repo the Project owns, even if the repo itself has no permissions-config entries of its own. Today's dashboard (and the `main.py` script it replaces, in its original form) never fetches this layer — it only asks each repo for its own Direct/Group permissions. As a result, a user or group with Project-level Admin access is completely invisible in the roster and in diffs between Runs. This undermines the tool's core purpose: an escalation that happens entirely at the Project level (e.g. a group's Project grant moving from read to admin) is exactly the kind of change an auditor most needs to see, and today it's silently missed.

## Solution

When a Run executes, the tool also fetches each distinct Project's own Direct and Group permissions (once per Project, not once per repo) and reflects them on every repo that Project owns, alongside that repo's own Repo-level grants — tagged by **Grant scope** (Repo-level vs Project-level) so it's clear where a permission actually comes from. A Principal can hold a Repo-level grant and a Project-level grant of the same kind on the same repo simultaneously, tracked as two independent records — never collapsed. If a Project's own permissions data can't be fetched (e.g. the credential lacks Project-level scope), the affected repos show that the Project layer is unknown without hiding data that *did* fetch successfully (the repo's own grants, or other Projects' data). Diffs between two Runs treat Project-level grants exactly like Repo-level ones: Grants, Revokes, and Escalations/Demotions are surfaced per repo, per the existing diff semantics.

## User Stories

1. As an auditor, I want to see users/groups with permissions granted at the Project level on a repo's roster, so that I don't miss access paths that never appear in that repo's own permissions-config.
2. As an auditor, I want Project-level Direct grants displayed distinctly from Repo-level Direct grants, so I understand where a user's access actually comes from.
3. As an auditor, I want Project-level Group grants displayed distinctly from Repo-level Group grants, for the same reason.
4. As an auditor, I want Project-level Member grants (a user's access via a Project-level group's resolved membership) shown per repo, so group-derived access via the Project is just as visible as group-derived access via the repo.
5. As an auditor comparing two Runs, I want an escalation that occurred via a Project-level grant to show up as an Escalation on every repo in that Project, so I can see the real exposure repo-by-repo rather than as one abstract "project changed" event.
6. As an auditor, I want a Repo-level grant and a Project-level grant of the same kind and level for the same user on the same repo to be tracked as two independent records, so that revoking one while the other remains doesn't look like a no-op change.
7. As an auditor, I want to know when a Project's own permissions data could not be fetched (e.g. HTTP 403), distinct from a specific repo's own fetch failing, so I can tell "the Project layer is unknown" apart from "this repo's own layer is unknown."
8. As an auditor, I want a repo whose own permissions fetched fine to still show its full roster even if that repo's Project fetch failed, so a Project-level failure doesn't hide data the tool did successfully collect.
9. As an auditor, I want the tool to fetch each Project's permissions only once per Run (not once per repo in that Project), so a workspace with many repos concentrated in a few Projects doesn't multiply API calls unnecessarily.
10. As an auditor, I want a group granted access at the Project level to have its membership resolved the same way as a repo-level group (an Unresolvable membership tracked distinctly from a genuinely empty group), so the existing membership-resolution semantics aren't weakened for this new scope.
11. As an auditor, I want moving a permission from Repo-level to Project-level between two Runs to show as a Revoke plus a Grant rather than being silently dropped or treated as a no-op, so I have full visibility into how access is structured over time, even when a change isn't a net change to real-world access.
12. As an auditor, when a Project has zero configured grants (fetched successfully, empty result), I want that treated distinctly from a Project fetch failure — matching how "Repo-level zero grants" is already distinct from "Repo-level Fetch failure" today.
13. As an auditor, I want a Discovery failure (the whole workspace listing failing) to remain a Run-aborting condition distinct from a Project fetch failure (scoped to one Project, Run continues), so partial Project-level outages don't block an entire audit Run.
14. As a developer maintaining this codebase, I want Project-level grants tested through the same seams as existing Repo-level grants (the `FakeBitbucketClient` in `collect.rs`, plus `diff.rs`/`roster.rs`/`storage.rs` unit tests) so regression coverage matches the codebase's existing established pattern.
15. As an auditor, I want a Project fetch failure to be visible in the roster tree itself for every repo it affects, not just logged to a console/terminal the dashboard user never sees.

## Implementation Decisions

- New `GrantScope` enum (`Repo` | `Project`) added as a field on `PermissionRecord`, orthogonal to the existing `AccessType` (`Direct`/`Group`/`Member`) — per ADR-0012. `AccessType` itself is unchanged; the same three grant kinds now apply at either scope.
- `BitbucketClient` trait gains two methods mirroring the existing repo-level ones: `list_project_direct_permissions(workspace, project_key)` and `list_project_group_permissions(workspace, project_key)`, reusing the existing `RawUserPermission`/`RawGroupPermission` shapes.
- `list_group_members` is reused unchanged for resolving a Project-level group's membership — membership resolution doesn't depend on which scope granted the group its access.
- `collect_and_store` (`collect.rs`) fetches each distinct `project_key`'s permissions at most once per Run, caching by `project_key` (same pattern as the existing `member_cache` keyed by group slug), and flattens the result into one `PermissionRecord` (with `scope: Project`) per repo owned by that project.
- New `ProjectFetchStatus` type mirroring `RepoFetchStatus`: tracks per-`project_key` fetch outcome (`Ok` | `FetchFailed`) once per Snapshot, not duplicated per repo.
- Failure handling for the two new client calls follows the existing convention: `Unauthorized` aborts the whole Run (same as today's repo/group handling); `RateLimited` (after the client's own retry)/`Other` marks that Project's `ProjectFetchStatus::FetchFailed` and the Run continues — independent of the repo-level `RepoStatus` for any repo in that Project.
- `diff.rs`'s `RecordKey` extends from `(repo, principal_id, AccessType)` to `(repo, principal_id, GrantScope, AccessType)`, so a Repo-level and a Project-level grant of the same kind/level never collide or collapse (extends ADR-0001, per ADR-0012).
- `roster.rs`'s `get_roster_tree` extends to carry `scope` on each grant row and to join `ProjectFetchStatus` onto every repo belonging to that Project, computed at query time — no caching/materialization, consistent with ADR-0004.
- `storage.rs`: `encode_access_type`/`decode_access_type` extend to persist/load the new `scope` field; a new table (or column set) persists `ProjectFetchStatus` per Snapshot per `project_key`.
- Domain vocabulary and rationale already recorded ahead of implementation: `CONTEXT.md` terms **Grant scope**, **Project**, **Project fetch failure** (and light updates to **Direct/Group/Member grant**); `docs/adr/0012-project-level-grants-orthogonal-scope.md`.

## Testing Decisions

Tests exercise each module's existing public seam and external behavior, not internals — matching this repo's established pattern (per `CLAUDE.md`: storage, diff engine, and fetch/orchestration are each covered by `cargo test` in `src-tauri`, no JS test runner is configured, and none is being introduced here since this is backend-only).

- `collect.rs`: extend the existing `FakeBitbucketClient` (already used for the PD-2/PD-3/PD-4/PD-5 repo-level tests) with project-permission fixtures. New cases: (a) a Project's permissions are fetched exactly once across multiple repos sharing that Project — asserted via a call-count fake, the same pattern already used for `group_members_call_count`; (b) resulting `PermissionRecord`s carry `scope: Project` and appear on every repo in that Project; (c) a Project-level fetch failure produces `ProjectFetchStatus::FetchFailed` for that Project while unrelated repos' and unrelated Projects' data stays intact; (d) `Unauthorized` on a project-level call aborts the whole Run, same as today's repo/group `Unauthorized` handling.
- `diff.rs`: pure unit tests (no I/O) asserting a Repo-level and a Project-level grant of the same `AccessType` and level, for the same principal + repo, diff as two independent records; a scope change between Runs (Repo → Project) diffs as a Revoke + Grant pair, matching ADR-0001's already-accepted trade-off.
- `roster.rs`: unit tests asserting the roster tree surfaces Project-level rows alongside Repo-level rows for the same repo, and that `ProjectFetchStatus::FetchFailed` appears against every repo in that Project without altering those repos' own `RepoStatus`.
- `storage.rs`: round-trip tests (encode → save → load → decode) for the new `scope` field and for `ProjectFetchStatus` persistence, following this module's existing round-trip test pattern.

## Out of Scope

- Frontend/UI rendering of Project-level rows (badges, drawer copy, visual treatment) — a follow-up ticket once this backend model exists.
- "Effective permission" collapsing across scopes (e.g. taking the max across a user's Repo-level, Project-level, and Member grants) — explicitly out of scope per ADR-0001 and unchanged by this work.
- Diffing Project membership or other Project metadata as its own entity — only a Project's Direct/Group grants and their cascade to repos are in scope, consistent with the existing non-goal that group membership isn't a diffable dimension.
- Any change to how `repo_project` is determined or displayed on existing records.
- Handling a repo moving between Projects mid-Run — not possible today, since `project_key` is captured once per repo per Run alongside repo discovery, same as `repo_project` already is.

## Further Notes

This closes a gap found against `main.py`'s current (uncommitted) reference version, which added exactly this project-level fetch after discovering repos whose access was configured only at the Project, never the repo itself — and which the existing Rust port had not yet picked up. Full domain rationale is recorded in `docs/adr/0012-project-level-grants-orthogonal-scope.md` and the `CONTEXT.md` terms **Grant scope**, **Project**, and **Project fetch failure**.
