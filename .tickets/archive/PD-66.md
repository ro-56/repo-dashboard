## Problem Statement

The head bar's global Apply button ("Apply {pendingCount} changes") is always visible, even when there is nothing staged to apply. Today it's just greyed out via a `disabled` attribute — the affordance for a batch write-back action sits in the header at all times, whether or not there's anything for it to do. This is inconsistent with the rest of the head bar (the Run-pair selectors and delta chips only render when relevant) and with the row-level edit menu (`RosterRow.svelte`), which is hidden outright rather than shown disabled when editing isn't currently possible.

## Solution

The Apply button only renders in the head bar when there is at least one staged Pending edit AND editing is currently enabled (the Comparison is the latest Snapshot, per ADR-0022). When neither condition holds, the button is absent from the DOM entirely rather than shown disabled.

## User Stories

1. As a user auditing repo permissions with no staged edits, I want the Apply button absent from the head bar, so that the header doesn't show an inert control with nothing to act on.
2. As a user who stages a Level-change or Remove on a Direct or Group grant, I want the Apply button to appear as soon as that first edit is staged, so that I have a clear, immediate affordance to commit it.
3. As a user who undoes their last remaining staged edit, I want the Apply button to disappear again, so that the header always reflects whether there's a live batch to commit.
4. As a user viewing an older Run pair (Comparison is not the latest Snapshot), I want the Apply button absent even if edits are somehow still held in local state, so that I can never attempt to apply a batch staged against a Comparison that's no longer current.
5. As a user who just completed a new Run while edits were staged, I want the Apply button to disappear along with the discarded Pending edits (existing ADR-0022 behavior), so that the header doesn't show a now-stale Apply affordance.
6. As a developer reading `HeadBar.svelte`, I want the button's visibility condition to be a single named, unit-tested function rather than inline boolean logic duplicated across the component and the page, so that the rule is easy to verify and reuse.

## Implementation Decisions

- Target is the existing `.apply-btn` in `HeadBar.svelte` (the single global Apply action defined in ADR-0022) — no new button, no change to what Apply does once clicked.
- Add a pure function `canApply(pendingCount: number, editingEnabled: boolean): boolean` to `headBar.ts`, alongside its other pure presentation-logic exports (`deltaChips`, `selectorOptions`, `snapshotSeqs`, `spanNote`). Returns `true` only when `pendingCount > 0 && editingEnabled`.
- `+page.svelte` replaces its inline `applyDisabled = pendingCount === 0 || !editingEnabled` derived value with a call to `canApply(pendingCount, editingEnabled)`, and passes the result to `HeadBar` as a prop named `canApply` (renamed from `applyDisabled`, sense inverted: `true` now means "show and enable," not "disable").
- `HeadBar.svelte` wraps the entire `.apply-btn` element in `{#if canApply}` — full conditional rendering, not a `disabled` attribute. This matches the existing precedent in the same component (selectors and delta chips already appear/disappear via `{#if}`) and in `RosterRow.svelte` (hides its edit menu entirely — `menu = null` — rather than rendering it disabled when editing isn't enabled).
- Because the button can only render when `canApply` is true, the button element no longer needs a `disabled` attribute or the disabled-state CSS (`.apply-btn:disabled`) — remove both.
- `openApplyDialog()` in `+page.svelte` keeps its existing guard clause, updated to `if (!canApply) return;` — retained as cheap defense-in-depth against any future caller (e.g. a keyboard shortcut) that might invoke it without going through the render-gated button.
- No change to the visibility-governing condition beyond the rename/inversion: it still combines `pendingCount === 0` and `!editingEnabled` into one gate, rather than keying visibility off `pendingCount` alone. This is deliberate — it does not rely on the cross-file invariant (the `$effect` in `+page.svelte` that clears `pending` on every `comparisonId` change) continuing to hold; if that invariant is ever broken by a future change, the button still correctly stays hidden.
- No layout reservation for the button's absence — the `.drawer-toggle` gear icon (next in the flex row, separated by `margin-left: auto` on the Apply button) shifts left instantly when Apply disappears, consistent with how the header already behaves when its other conditional elements (selectors, delta chips) are absent.
- No `CONTEXT.md` changes — the glossary's existing "Apply" entry describes the action, not the button's visibility, and its definition is unchanged. No ADR — every choice here matches an established pattern already present in the codebase (RosterRow's hide-not-disable precedent, HeadBar's own existing conditional rendering) rather than a fresh architectural trade-off.

## Testing Decisions

- A good test here exercises `canApply`'s external behavior (its four boolean-input combinations and their expected output) — not `HeadBar.svelte`'s markup or `+page.svelte`'s wiring, which stay untested per ADR-0017 (Svelte component/page rendering tests are deferred to Playwright, not backfilled with vitest).
- New colocated `headBar.test.ts` covering `canApply`: all four combinations of `pendingCount` (zero / non-zero) × `editingEnabled` (true / false), asserting the button is eligible to show only when both `pendingCount > 0` and `editingEnabled` are true.
- Prior art: `pendingEdits.test.ts` already unit-tests this module's sibling pure-logic file (`pendingEdits.ts`) the same way — small, input/output-focused cases with no DOM or component involved.
- Manual verification via `pnpm tauri dev`: stage an edit and confirm the button appears; undo it and confirm it disappears; switch the Comparison to an older Snapshot and confirm it stays absent even before any edit is staged; complete a new Run while edits are staged and confirm it disappears along with the discarded edits.

## Out of Scope

- Any change to what happens when Apply is clicked, the confirm dialog, or the batch-apply request/response handling (`pendingEdits.ts`'s `toApplyPayload`/`settleApplied`/`resultRows`, `apply_pending_edits`).
- Any change to `editingEnabled`'s own definition or to when Pending edits are staged/cleared.
- Layout animation or reserved space for the button's appearance/disappearance.
- Any change to the row-level edit menu's existing hide-when-not-editable behavior (`RosterRow.svelte`) — referenced here only as precedent, not touched.

## Further Notes

This was scoped via a `/grill-with-docs` session (`/workspace/.claude/skills/grill-with-docs`) walking through: button identity, hide-vs-disable, the visibility condition's exact shape, prop renaming, the guard clause, and layout-shift tolerance — each confirmed individually before this spec was written. No ADR or CONTEXT.md update was warranted; the session's conclusion was that every decision here reuses an existing codebase pattern rather than introducing a new one.
