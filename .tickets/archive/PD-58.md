## Problem

\`Permission::parse()\` (\`src-tauri/src/model.rs\`) only recognizes \`"read"\`, \`"write"\`, \`"admin"\`. Bitbucket's Project-level \`permissions-config\` API also accepts \`create-repo\` (and \`none\`) — a real, valid value, project-scope only.

Every normalize function that parses a permission string panics on anything else:

\`\`\`rust
Permission::parse(&p.permission).unwrap_or_else(|| panic!("invalid permission string: {}", p.permission))
\`\`\`

This appears in \`normalize_repo_permissions\`, \`normalize_project_permissions\`, \`normalize_repo_group_permissions\`, and \`normalize_project_group_permissions\` (\`src-tauri/src/normalize.rs\`).

So: any workspace where a user or group has been granted \`create-repo\` at the Project level will panic during \`collect_and_store\`'s normalize step on the next Run. Unlike the existing per-repo 404 handling (PRD §5.2 — one inaccessible repo shouldn't fail the whole snapshot), there's no per-record recovery here — this looks like it would crash the whole Run rather than degrade gracefully.

## Discovered during

Grilling session for the permission-editing feature (see ADR-0021/0022/0023, \`docs/adr/\`) — that feature deliberately keeps its *edit* UI restricted to read/write/admin (a distinct, intentional scope decision), but this bug is on the *read* path and pre-dates that work entirely.

## Suggested fix direction

Don't panic on an unrecognized permission string. Options to weigh: skip the record with a logged warning (mirrors how a 404'd repo already degrades instead of failing the Run), or introduce an explicit "unmodeled permission" status distinct from the existing Read/Write/Admin enum so it's visible in the roster rather than silently dropped. Needs its own grilling session to decide which.
