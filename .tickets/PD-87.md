## Problem Statement

When an auditor uses repo-dashboard to remove or downgrade a Principal's access (a staged Level-change or Remove against a Direct or Group grant), the tool mutates live Bitbucket permissions but keeps no record of *why* that decision was made. Once Apply fires, the reasoning behind a permission change lives only in the auditor's memory (or an external channel this tool has no visibility into) — there is no durable, in-tool answer to "why was this person's access removed, and when."

## Solution

Let the user attach an optional, free-text Justification to a Pending edit at the moment they stage it (choosing a new level or Remove in a row's edit menu). If that specific edit is later applied successfully, the Justification — along with the account that applied it and the moment it took effect — is written to a new, durable Applied-edit log, kept entirely independent of Snapshot lifecycle so it survives routine Snapshot deletion (ADR-0011). The Justification is shown back to the user in the existing Apply results view. A dedicated browser/viewer for the Applied-edit log is out of scope for this round.

## User Stories

1. As an auditor, I want to type a short reason when I remove a Direct grant, so that there's a record of why that access was revoked.
2. As an auditor, I want to type a short reason when I change a Direct or Group grant's level (e.g. Admin → Write), so that a future reviewer understands the intent behind the downgrade, not just the fact of it.
3. As an auditor, I want the Justification field to be optional, so that I'm not blocked from staging or applying an edit when I don't have (or don't want to give) a reason.
4. As an auditor, I want to type the Justification inline, right where I pick the new level or Remove, so that I record my reasoning at the moment I'm making the decision, not after the fact.
5. As an auditor, I want my Justification to only be recorded once the edit actually takes effect on Bitbucket, so that a failed apply attempt (insufficient scope, rate limiting, a 404) doesn't produce a misleading "this change happened" record.
6. As an auditor, I want a failed edit to keep its Justification intact while it stays staged for retry, so that I don't have to retype my reasoning if the first attempt failed.
7. As an auditor, I want to see the Justification I wrote reflected in the Apply results view after a batch completes, so that I can confirm what was recorded.
8. As an auditor, I want the timestamp recorded against my Justification to represent when the change actually took effect on Bitbucket, so that "when" answers the question that matters for an audit — not when I merely started drafting the edit.
9. As an auditor, I want the Applied-edit log to record which account performed the change, so that a shared-desktop scenario still attributes changes to whoever was logged into the app's stored credential at the time.
10. As an auditor, I want the Applied-edit log to survive even if I later delete the Snapshot the edit was staged against, so that routine Snapshot cleanup (ADR-0011) never silently destroys my audit trail.
11. As an auditor removing a Group grant (which cascades to derived Member grants), I want my one Justification for that Group edit to cover the whole action, so that I'm not asked to justify each individually-derived Member grant separately (Member grants aren't independently editable, per ADR-0021).
12. As a developer, I want the Justification and Applied-edit log persistence logic covered by backend unit tests using the existing mock-client pattern, so that the feature's correctness doesn't depend on manual verification of live Bitbucket calls.
13. As a developer, I want the frontend's pending-edit staging/confirm/result view models to have colocated unit tests for the new Justification field, consistent with how `pendingEdits.ts` is already tested.

## Implementation Decisions

- **Scope of applicability**: Justification applies to both `SetLevel` and `Remove` Pending edit actions — matches the ticket's own "removes or changes" framing. It does not apply to Member grants, since those have no independent edit menu at all (ADR-0021).
- **Optionality**: The field is optional at every step — staging, review/confirm, and Apply. No client- or server-side validation blocks an edit with a blank Justification.
- **Capture point**: Typed inline, per staged edit, in the row's existing edit menu (`RosterRow.svelte`) at the moment the user picks a level or Remove — not deferred to the Confirm Apply dialog. It becomes part of the same `StagedEdit`/`PendingEditRequest` object already staged for that row, so it follows the edit's existing lifecycle exactly (replaced if the same slot is re-staged, cleared on Undo, discarded wholesale if a new Run/Refresh supersedes the Comparison Snapshot per ADR-0022).
- **Text constraints**: Free text, no reason-code taxonomy. Soft max length of 500 characters, app-enforced (not merely relying on SQLite's own TEXT limits).
- **Wire contract**: `PendingEditRequest` (both `src-tauri/src/apply.rs` and `src/lib/pendingEdits.ts`) gains a new optional `justification: Option<String>` / `justification?: string` field, serialized the same way as the rest of the struct (`camelCase` on the wire). `StagedEdit` carries the same field so the UI can redisplay it.
- **New persisted entity — the Applied-edit log**: A new SQLite table (schema added to `storage.rs`'s existing `CREATE TABLE IF NOT EXISTS` block, following the same lazy-migration pattern as `snapshots`/`permission_records`/etc.). One row per **successfully applied** edit, with columns: repo/project, repo, Principal id/label, `AccessType`/target (Direct or Group), scope (Repo/Project), action (SetLevel-to-level or Remove), before-level, after-level (nullable/omitted for Remove), `justification` (nullable text), `applied_at` (RFC3339 timestamp string, same format `run_at` already uses elsewhere in `lib.rs`), and `account` (the string from the stored `Credentials.username`, relabeled in UI/docs as "account" rather than claimed as a verified email — no schema change to `Credentials` itself).
- **No Snapshot coupling**: The Applied-edit log table has **no** `source_snapshot_id` column and no foreign key into `snapshots`. This is deliberate (ADR-0032) — Snapshots are freely deletable at any time (ADR-0011) as routine cleanup unrelated to whether an edit staged against one was ever applied; tying the log to a Snapshot id would force a choice between a dangling reference or cascading the justification away, defeating the log's purpose.
- **Persistence trigger — success only**: A log row is written only when `apply_pending_edits` reports a successful `ApplyResult` for that specific edit. A failed attempt (`Unauthorized`, `RateLimited`, `Other`) writes nothing; the edit stays staged in frontend state for retry (existing `settleApplied` behavior in `pendingEdits.ts` is unaffected — it already only clears successfully-applied edits from the staged map). If a later retry of the same edit succeeds, that later attempt is what gets logged, with whatever Justification text is staged at that time.
- **Backend seam**: `apply::apply_pending_edits` (`src-tauri/src/apply.rs`) is extended to accept a `&mut rusqlite::Connection`, an `applied_at: &str` timestamp, and an `account: &str`, alongside its existing `client`/`workspace`/`edits` parameters — mirroring the shape `collect_and_store` and `refresh_and_store` already use for connection + timestamp injection. After computing each edit's `ApplyResult`, the function writes an Applied-edit log row for every success before returning the same `Vec<ApplyResult>` as today. This keeps the "which edits get logged and what the row contains" decision in one already-tested function rather than spreading it across the Tauri command layer.
- **Tauri command wiring**: `apply_pending_edits` in `lib.rs` becomes a thin wrapper that additionally takes `db: tauri::State<'_, DbState>`, computes `applied_at` via `chrono::Utc::now().to_rfc3339()` (same pattern as `run_now`/`refresh_snapshot`), reads `account` from the already-fetched `creds.username`, and passes both plus a locked `conn` down into `apply::apply_pending_edits`.
- **Surfacing after apply**: `ConfirmApplyDialog.svelte`'s results view (`phase === "results"`) displays the Justification text (if present) alongside each `ResultRow`, so the user sees what was recorded immediately after Apply completes. `pendingEdits.ts`'s `resultRows`/`ConfirmRow`/`ResultRow` types gain a `justification` field threaded through from the corresponding `StagedEdit`.
- **No actor/auth model change**: The `account` field is a best-effort label reusing the existing single stored credential's `username` — this does not introduce login, roles, or any multi-user concept, consistent with the project's explicit non-goals.
- **Viewer deferred**: No new panel/route is built to browse the Applied-edit log's history in this round. The log is written and (partially) shown in the results view only; a future ticket can add a dedicated browsing UI.

## Testing Decisions

- Good tests here exercise observable behavior — what gets logged and what doesn't — not internal call order. For the backend, that means: given a mix of staged edits (some with Justification, some without) and a mock `BitbucketClient` configured to succeed on some and fail on others, assert on the resulting `Vec<ApplyResult>` (unchanged shape/behavior) *and* on the rows actually present in the Applied-edit log table afterward (queried directly via the same in-memory `Connection`) — never on internal function call counts.
- **Backend — `src-tauri/src/apply.rs`**: extend the existing `#[cfg(test)] mod tests` (already using a mock `BitbucketClient` and asserting on `Call` history) to also pass an in-memory `rusqlite::Connection::open_in_memory()` (matching `storage.rs`'s own test pattern) with the Applied-edit log schema created. New cases: (a) a successful `SetLevel` edit with a Justification produces exactly one log row with the right before/after levels and text; (b) a successful `Remove` edit with no Justification produces a log row with a null/absent justification; (c) a failed edit produces zero log rows; (d) a batch mixing successes and failures logs only the successes; (e) `applied_at`/`account` are recorded verbatim from the parameters passed in.
- **Backend — `storage.rs`**: if the log's insert/schema logic is factored into a small helper (e.g. `insert_applied_edit`), it follows the same `Connection::open_in_memory()` test convention already used for `snapshots`/`permission_records` in that file's `mod tests`.
- **Frontend — `src/lib/pendingEdits.ts`**: extend the existing `pendingEdits.test.ts` (already covers `stageEdit`, `confirmRows`, `resultRows`, `settleApplied`, etc. using the `levelEdit`/`removeEdit` fixture-builder pattern) with cases for: staging an edit with/without a Justification preserves it through `confirmRows`; `toApplyPayload` includes the `justification` field on the wire; `resultRows` surfaces the Justification text for a matched result; an edit staged with no Justification round-trips as `undefined`/absent rather than an empty string.
- **Not tested via automation**: `RosterRow.svelte`'s new inline Justification input and `ConfirmApplyDialog.svelte`'s display of it are Svelte components — per ADR-0017, verified manually via `pnpm tauri dev` (stage a Remove/level-change with and without a Justification, confirm/apply, and check the results view), not via Playwright (still an unused devDependency).

## Out of Scope

- A dedicated UI to browse/search the Applied-edit log's full history (future ticket).
- Making the Justification mandatory, or adding any minimum-length validation.
- Adding a `source_snapshot_id` or any other foreign key from the Applied-edit log back to `Snapshot`.
- Logging failed apply attempts in any form.
- Any new identity/auth concept beyond reusing the existing stored `Credentials.username` as a best-effort "account" label.
- Exporting the Applied-edit log via the existing CSV Roster export (ADR-0026) — that export remains a flat, diff-free Roster snapshot and is untouched by this feature.
- Adding a new Permission level, reason-code taxonomy, or structured category for Justifications — it stays a single free-text field.

## Further Notes

- This spec assumes ADR-0032 (`docs/adr/0032-applied-edit-log-decoupled-from-snapshot.md`) and the two new `CONTEXT.md` glossary terms (`Justification`, `Applied-edit log`) are already committed — they were written and confirmed with the user in the design discussion that produced this spec.
- The `account` field's honesty (it's whatever string is in `Credentials.username`, not a verified email) should be reflected in whatever label the results view/log uses — avoid calling it "email" anywhere user-visible.
- Because the Applied-edit log has no relationship to Snapshots, deleting every Snapshot in the app (via `delete_snapshot`, ADR-0011) has no effect on the Applied-edit log's contents — this is intentional and worth a passing regression check if `delete_snapshot`'s own tests are touched in the same PR.
