## Problem Statement

When a user clicks "Get all data" in the Run panel, the button just reads "Running…" with no other feedback until the whole Run finishes or fails. A workspace can have dozens of repos, and each repo's fetch involves several sequential Bitbucket API calls (direct grants, group grants, occasional Project-level grants), so a Run can take a while. During that time the user has no way to tell whether the app is making progress, stalled, or about to fail — they just have to wait and hope.

## Solution

While a Run is in flight, the Run panel (inside the existing credentials/run SideDrawer, ADR-0010) shows which repo is currently being fetched and how far through the Run we are, e.g. "Fetching: repo-a (2/12)", backed by a determinate progress bar (2 of 12 filled). The count and repo name update live as the Run works through the repos discovered for the workspace, giving the user a clear, honest sense of progress without changing any of the Run's existing data-collection or failure semantics.

## User Stories

1. As a user running a Run, I want to see which repo is currently being fetched, so that I know the app is actively working and not stalled.
2. As a user running a Run, I want to see a running count like "(2/12)", so that I know roughly how much longer the Run will take.
3. As a user running a Run, I want a visual progress bar alongside the text, so that I can gauge progress at a glance without reading numbers.
4. As a user running a Run on a workspace with many repos, I want the progress count to be based on the total number of repos discovered, so that the bar reflects real, known scope rather than an indeterminate guess.
5. As a user running a Run, I want the counter to reflect the repo currently in flight (1-indexed, e.g. the first repo shows "(1/12)" as soon as its fetch starts), so the number I'm reading matches what's happening right now.
6. As a user running a Run, I want a repo whose Project is being fetched for the first time (Project-level grants, cascading to every repo the Project owns) to still just read as that one repo's progress tick, so that the count I'm watching stays simple and matches the repo total I already understand from the roster.
7. As a user running a Run before repo discovery has completed, I want the panel to keep showing today's plain "Running…" state (no bar, no count) until the repo total is known, so that I'm never shown a fabricated or flickering total.
8. As a user running a Run where one repo hits a Fetch failure (recorded per repo, per `CONTEXT.md`) partway through, I want the progress line to keep advancing to the next repo without interruption or a special error indicator, so that a single repo's trouble doesn't make the whole Run look broken — I'll see the failure reflected in the roster tree afterward, same as today.
9. As a user running a Run that aborts entirely (Discovery failure or a mid-Run credential rejection), I want the existing error message behavior to take over exactly as it does today, so that progress reporting doesn't change or duplicate existing error handling.
10. As a user, I want the progress panel to only be visible while the SideDrawer is open, so that closing the drawer mid-Run behaves exactly like it does today (the Run keeps going in the background) and reopening the drawer shows me current progress again.
11. As a developer maintaining `collect_and_store`, I want progress reporting to flow through the same kind of injected, fake-able seam already used for `BitbucketClient`, so that the full progress sequence for a Run (including repos with Fetch failures, cached Project fetches, etc.) stays covered by `cargo test` without needing a real Tauri runtime.

## Implementation Decisions

- **New type `RunProgress`** in `collect.rs`: `{ index: u32, total: u32, repo: String }`. `index` is 1-indexed ("currently fetching repo `index` of `total`"). `repo` is the repo slug only (not `project/repo` — the Project is visible elsewhere in the roster tree, and repo slugs are the identifier already used in this panel's context).
- **`collect_and_store` signature change**: add a `progress: &mut impl FnMut(RunProgress)` parameter. Called exactly once per repo in the main discovery loop, immediately before that repo's own calls begin (direct grants, group grants, and — only for the first repo of a given Project in this Run — that Project's own Direct/Group grant calls, per the existing `project_cache` in `collect.rs`). A repo's Project-level work is never reported as a separate tick; it's folded silently into that repo's single progress call. `total` is the length of the repo list returned by discovery, computed once before the loop starts and passed unchanged on every call.
- **No progress call during discovery** (`list_repositories`) — the first call to `progress` happens only once discovery has succeeded and the loop begins.
- **No progress semantics change on failure**: a repo-level `FetchFailed` (direct or group grants) does not change what gets passed to `progress` for that repo or any other — the callback only ever carries `{index, total, repo}`, never a status. Existing `RunError` abort paths (`CredentialRejected`, `DiscoveryFailed`) are unaffected; a mid-Run abort simply means no further `progress` calls happen and `collect_and_store` returns `Err` as it does today.
- **`run_now` (in `lib.rs`)**: passes a closure to `collect_and_store` that calls `app_handle.emit("run-progress", progress)`, where `app_handle: tauri::AppHandle` is obtained from Tauri's managed state/app handle the way other commands already access app resources. This closure is the only new code in `run_now` — no other change to its control flow, error mapping, or return type.
- **Architecture decision, recorded as ADR-0013** (`docs/adr/0013-run-progress-via-injected-callback.md`): progress is threaded through `collect_and_store` via an injected callback rather than passing `tauri::AppHandle` directly into the function, preserving its existing Tauri-free, fully-`cargo test`-able design (mirrors the `BitbucketClient` trait/fake pattern already in use).
- **Frontend (`RunPanel.svelte`)**: on `runNow()`, before calling `invoke("run_now")`, set up a listener via `@tauri-apps/api/event`'s `listen("run-progress", …)` that updates local `$state` (`progressIndex`, `progressTotal`, `progressRepo`). Unsubscribe the listener in the `finally` block alongside the existing `running = false` reset. While `running` is true and no progress event has arrived yet, keep today's "Running…" button label (covers the discovery phase). Once the first `run-progress` event arrives, render the repo/count text (e.g. "Fetching: repo-a (2/12)") and a determinate progress bar (`progressIndex / progressTotal`) in place of/alongside the button, styled per the drawer's existing token set (`src/lib/styles/tokens.css`). No change to `SideDrawer`'s open/close behavior — the progress UI simply lives inside `RunPanel` and is unmounted/hidden exactly when the drawer is closed, same as the rest of the panel today.
- **No new Tauri commands** — `run_now`'s signature and return type are unchanged; progress is purely an out-of-band event stream alongside the existing awaited command.
- **No `CONTEXT.md` changes** — progress reporting is UI/observability behavior, not a new domain concept; it doesn't touch Run, Snapshot, Fetch failure, or any other glossary term's definition.

## Testing Decisions

- All new behavioral coverage lives in the existing `collect.rs` test module, extending the established `FakeBitbucketClient` + `cargo test` pattern already used for every other `collect_and_store` behavior (discovery, per-repo failures, group membership caching, Project-level caching/failures).
- Tests pass a closure that pushes each `RunProgress` into a `Vec`, then assert on the captured sequence: e.g. total matches repo count, index increments 1..=N in discovery order, a repo whose Project is being fetched for the first time still produces exactly one `RunProgress` for that repo, and a repo-level `FetchFailed` does not suppress or alter that repo's `RunProgress` call. A mid-Run abort (`CredentialRejected`/`DiscoveryFailed`) should show no `RunProgress` calls after the point of failure, and (for `DiscoveryFailed`) no calls at all.
- `run_now`'s closure and the frontend listener/rendering in `RunPanel.svelte` are thin wrappers, consistent with the rest of `lib.rs` (no dedicated tests for command wrappers) and the rest of the frontend (no JS test runner configured in this repo, per `CLAUDE.md`) — verified manually via `pnpm tauri dev` instead.

## Out of Scope

- Cancelling an in-flight Run. No cancel button, no cooperative cancellation threaded through `collect_and_store`, no decision about partially-saved Snapshots on cancel.
- Any live indication of per-repo failure inside the progress line itself (no color change, no inline failure count) — failures continue to surface only in the roster tree after the Run completes, as today.
- A persistent progress indicator visible outside the SideDrawer (e.g. in `HeadBar`) when the drawer is closed.
- Any change to `RunError` variants, `run_now`'s error mapping, or the Run's abort semantics on `CredentialRejected`/`DiscoveryFailed`/`StorageFailed`.
- Reporting progress at a finer grain than one tick per repo (e.g. separate ticks for direct-grants vs group-grants vs Project-level calls within a single repo).
- Polling-based progress (a `get_run_progress` command backed by shared Mutex state) — superseded by the Tauri-events decision above.

## Further Notes

- This spec assumes Tauri v2's `AppHandle::emit` is available synchronously from within the closure passed into `collect_and_store` without requiring `.await`, consistent with how `run_now` already holds a `tokio::Mutex` guard across `.await` points elsewhere in the same function.
- The progress bar's visual styling (exact colors, animation, whether it reuses an existing token like the ones in `SummaryBar`/`CountBadges`) is left to implementation-time judgment within the existing `tokens.css` system — this spec fixes behavior and data flow, not pixel-level styling.
