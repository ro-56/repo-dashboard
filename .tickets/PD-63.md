## Problem Statement

`Permission::parse` only recognizes `read`, `write`, and `admin`. Bitbucket's Project-level `permissions-config` API also accepts `create-repo` — a real, valid value (verified against Atlassian's docs: the true Project hierarchy is `Admin ⊃ Create ⊃ Write ⊃ Read`, each level including everything below it). Every normalize function panics on any unrecognized permission string via `.unwrap_or_else(|| panic!(...))`, so any workspace where a user or group holds `create-repo` at the Project level crashes the entire Run's normalize step — not just the one repo/project involved. There is no per-record recovery, unlike the existing per-repo fetch-failure handling.

## Solution

Model `create-repo` as a real, fourth `Permission` value — visible on its own wherever a permission is displayed directly — but collapse it onto `Admin` everywhere the code computes rather than displays (diff classification, roster summary counts), per the "admin-light" decision recorded in ADR-0024. Any permission string that is genuinely unrecognized (neither `read`, `write`, `create-repo`, nor `admin`) is skipped at record granularity with a logged warning, rather than panicking — mirroring how a fetch failure already degrades gracefully instead of failing the whole Run.

## User Stories

1. As an auditor, I want a Run to complete successfully even when a Project has a user or group granted `create-repo`, so that I don't lose visibility into the rest of the workspace because of one permission value.
2. As an auditor, I want to see `create-repo` displayed as its own distinct permission level on a roster row, so that I know exactly which access a principal holds rather than having it silently relabeled as `admin`.
3. As an auditor comparing two Runs, I want a transition from `Write` to `create-repo` to be flagged as an Escalation, so that I notice when someone gains repo-creation capability.
4. As an auditor comparing two Runs, I want a transition between `create-repo` and full `Admin` (either direction) to NOT be flagged as any kind of change, so the diff isn't cluttered with movement between two levels this tool treats as equivalent audit severity.
5. As an auditor viewing the roster's summary counts, I want a principal holding `create-repo` counted alongside admins in the "N admins" figure, so headline numbers reflect real audit severity instead of undercounting a near-admin grant as zero.
6. As an auditor viewing a repo card's distribution bar, I want `create-repo` grants represented in the admin segment of the bar, so I get a rough sense of admin-tier exposure without a special case.
7. As an auditor, if Bitbucket ever returns some future or unexpected permission string (neither `read`, `write`, `create-repo`, nor `admin`), I want that one record skipped with a warning logged, rather than the whole Run crashing, so one unexpected value never takes down the entire audit.
8. As a developer maintaining this codebase, I want `Permission`'s own `Ord`/`Eq` to stay true to Bitbucket's real hierarchy (`Read < Write < CreateRepo < Admin`), so any future direct comparison of `Permission` values is trustworthy without special-casing.
9. As a developer maintaining the diff/count logic, I want one dedicated helper for the `CreateRepo → Admin` collapse, so escalation/demotion classification and roster counts can't drift into reimplementing the collapsing rule differently.
10. As an auditor, I want a `create-repo` escalation's tag to read "escalation → admin" (not a separate "escalation → create-repo" wording), consistent with treating it as admin-equivalent severity.
11. As a developer, I want `create-repo` to round-trip correctly through Snapshot storage (SQLite), so historical Runs retain the real distinction even though computations collapse it.
12. As an auditor, I want this fix scoped to the backend plus minimal frontend labeling only — not a full visual redesign of the distribution bar — so the crash gets fixed without dragging in unrelated design work.

## Implementation Decisions

- `model.rs`: `Permission` gains a `CreateRepo` variant, declared in true hierarchy position (`Read < Write < CreateRepo < Admin`), so the derived `Ord` stays meaningful for any direct comparison.
- `Permission::parse` recognizes `"create-repo"` (case-insensitive) → `Permission::CreateRepo`. It continues to return `None` for anything else — the panic removal happens at the call sites, not in `parse` itself.
- New method `Permission::admin_light(self) -> Permission` collapses `CreateRepo → Admin`, passing every other variant through unchanged. This is used *only* by diff/count computation, never by anything rendering a permission for display.
- `normalize.rs`: all four normalize functions (`normalize_repo_permissions`, `normalize_project_permissions`, `normalize_repo_group_permissions`, `normalize_project_group_permissions`) replace `Permission::parse(...).unwrap_or_else(|| panic!(...))` with: on `None`, skip that one record (don't include it in the returned `Vec<PermissionRecord>`) and log a warning containing the raw string, repo/project, and principal id. The containing repo/project's fetch status stays `Ok` — this is a per-record data anomaly, not a fetch failure, and must not be conflated with `RepoStatus::FetchFailed`.
- `storage.rs`: `permission_to_str`/`permission_from_str` gain a `"create-repo"` round-trip arm so the value survives Snapshot persistence and reload.
- `diff.rs`: the "did this record change" equality check and the Escalation/Demotion classification both compare `.admin_light()`-collapsed values instead of raw `Permission`. The `LevelChange::from`/`to` fields keep the raw, uncollapsed `Permission` — the collapse only affects *classification*, not what's recorded for display.
- `roster.rs`: `LevelCounts` and each `RepoNode`'s `read_count`/`write_count`/`admin_count` computation runs `.admin_light()` on the permission before matching, so `CreateRepo` folds into the existing `admin` bucket. No new count field is introduced.
- Frontend `roster.ts`: the `Permission` union type gains `"CreateRepo"`.
- Frontend `rosterRow.ts`: `RANK` and `LEVEL_CLASS` both map `CreateRepo` to the same value as `Admin` (same sort position, same `lvl-admin` styling). `levelWord` must render `"create-repo"` (hyphenated) rather than a blind `.toLowerCase()` of the serialized variant name (which would produce `"createrepo"` with no hyphen) — needs an explicit label mapping, not the current generic lowercase.
- The escalation tag logic (currently `status.to === "Admin" ? "escalation → admin" : "escalation"`) extends to also match `status.to === "CreateRepo"`.
- No `GrantScope` validation is added anywhere to enforce that `create-repo` only appears on Project-scoped records. Bitbucket's own API contract already guarantees this (the repo-level endpoint never returns it); validating it in this codebase would be defensive coding for a scenario that can't occur.
- Full rationale for the "distinct but computed as admin" split lives in ADR-0024 (`docs/adr/0024-create-repo-modeled-distinct-computed-as-admin.md`) and the `CONTEXT.md` "Create-repo permission" glossary entry — both already written; reference them in code comments rather than re-deriving the reasoning inline.

## Testing Decisions

Tests should exercise external behavior (parsed/collapsed values in, diff/roster output out) through each module's existing public seam — no new test infrastructure, no reaching into private helpers.

- `model.rs` (new colocated `#[cfg(test)] mod tests`, its first): `parse` recognizes `"create-repo"` case-insensitively; `parse` returns `None` for a nonsense string; `admin_light` collapses `CreateRepo → Admin` and passes `Read`/`Write`/`Admin` through unchanged.
- `normalize.rs` (existing test module): each normalize function gets a case where a `"create-repo"` raw permission produces a `CreateRepo` record with `Ok`/normal status; at least one function gets a case where a genuinely unrecognized string produces zero records but a normal (not `FetchFailed`) status.
- `diff.rs` (existing test module): `Write → CreateRepo` produces an `Escalation` `LevelChange`; `CreateRepo` on one side and `Admin` on the other (both directions) produces no `RecordDiff` at all.
- `roster.rs` (existing test module): a `CreateRepo` record contributes to `admin_count`/`LevelCounts.admin`, not a separate bucket.
- `rosterRow.test.ts` (existing file): `compareEntries` ranks `CreateRepo` alongside `Admin`; `deriveRow`'s `levelClass` maps `CreateRepo` to `"lvl-admin"`; `levelWord` renders `"create-repo"`; the escalation tag reads "escalation → admin" when `to === "CreateRepo"`.

Follow each file's existing fixture-helper conventions (e.g. `record()`/`group_record()` builders in the Rust test modules) rather than introducing new ones.

## Out of Scope

- Giving `create-repo` its own visual segment in the repo card's distribution bar (ADR-0008) — deferred to a follow-up ticket per ADR-0024.
- Modeling a `none` permission value. Investigated during the design discussion and confirmed not to be a real documented value for this endpoint (Atlassian's docs list exactly `read`, `write`, `create-repo`, `admin`) — ADR-0021's earlier mention of `none` was an unverified assumption. No code should be written for it.
- Any change to the permission-editing feature's scope (ADR-0021) — its level picker intentionally stays Read/Write/Admin only; this ticket doesn't touch editing at all, only the read/normalize path.
- `GrantScope` validation enforcing that `create-repo` only appears on Project-scoped records.
