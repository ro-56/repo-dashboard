## Problem Statement

The dashboard's implemented visual design (`src/lib/styles/tokens.css` and its consuming components) is built against a set of prototype files (`.references/dashboard_designs.html`, `.references/standalone/*.html`) that have since been deleted and replaced by a refined v2 design (`.references/new-design/`: `perm-diff.css` plus light/dark rendered mockups). The v2 design carries a different color/spacing/geometry token scale, a redesigned head bar (delta chips replacing the current-state summary bar), and — for the first time — a complete dark theme, none of which exist in the shipped app today.

Separately, two pieces of already-shipped backend data never made it into the UI at all: `PrincipalEntry.scope` (Repo-level vs Project-level grants, ADR-0012/PD-30) is computed and typed on the frontend but never rendered by any row, and `RepoNode.project_fetch_failed` (a Project's own fetch failing, ADR-0012) is computed and serialized correctly by the Rust roster tree but is missing from the TypeScript `RepoNode` interface entirely, so it is silently dropped before any component can see it. Both gaps were surfaced and resolved during a design-review session and are folded into this same pass since fixing them means touching the same roster-row and repo-card surfaces the v2 design already touches.

## Solution

Port the v2 design (`.references/new-design/`) into the app end-to-end: replace `tokens.css`'s token values and add its dark-theme block, rebuild the head bar around delta chips (retiring `SummaryBar.svelte`'s current-state cluster per ADR-0015), rebuild the filter bar/notice-strip/roster grid/repo-card chrome to the v2 geometry, and add a persisted light/dark theme toggle inside the side drawer (ADR-0016). While touching the roster row, also surface Grant scope as a `· project` suffix on the source column (ADR-0014) and wire `project_fetch_failed` through to a repo-card tag (no notice-strip sentence). All decisions below were already resolved in a prior grilling/domain-modeling session and recorded as ADR-0014, ADR-0015, and ADR-0016; this spec operationalizes them.

## User Stories

1. As an auditor viewing the dashboard, I want the visual design to match the finalized v2 mockups (`.references/new-design/`), so that the shipped app reflects the design that was actually approved.
2. As an auditor, I want permission level to still be conveyed only by weight/shape/position (never hue) under the new token set, so that the two-channel encoding rule (ADR-0005) survives the visual refresh unchanged.
3. As an auditor, I want diff state (Grant/Revoke/Level change/Escalation) to still be conveyed by hue + sigil + gutter under the new tokens, so that nothing about how I read a row's meaning changes, only its exact colors/spacing.
4. As an auditor, I want escalations to still always carry the amber wash, `↑` glyph, and tag with no way to turn it off, so that ADR-0007's always-on guarantee survives the redesign.
5. As an auditor, I want the roster grid's grant-source column to still never shed at any window width, so that ADR-0009's reflow order survives the redesign.
6. As an auditor, I want a Project-level grant's source cell to read e.g. `direct · project` instead of plain `direct`, so that I can tell at a glance whether a grant lives on the repo itself or cascades from its owning Bitbucket Project.
7. As an auditor, I want a Repo-level grant's source cell to render exactly as it does today (no suffix), so that the common case isn't visually noisier than before.
8. As an auditor, I want the same suffix convention applied to `group` and `grp:<name>` source labels when their grant is Project-level, so that scope is visible regardless of which grant kind (Direct/Group/Member) it modifies.
9. As an auditor hovering a truncated source cell, I want the tooltip to show the full, unabbreviated source-plus-scope text, so that ellipsis truncation never hides which scope a grant is at.
10. As an auditor, I want a repo whose owning Project failed to fetch this run to show a `project fetch failed` tag on that repo's card header, so that I know the Project-level layer's data is unreliable for that repo even though the repo's own fetch succeeded.
11. As an auditor, I want `project fetch failed` to be visually and textually distinct from a repo's own `fetch failed` tag, so that I don't conflate a Project-level failure with a repo-level one (CONTEXT.md distinguishes these explicitly).
12. As an auditor, I do NOT want a Project fetch failure to add a new sentence to the structural notice strip, so that the strip doesn't grow longer for a fact that's already visible as a per-repo-card tag.
13. As an auditor, I want the head bar to show delta-only chips (`+N added`, `−N revoked`, `~N changed`, `↑N escalations`) plus a terse trend line (e.g. "13 days · 486 → 492 grants"), so that the most important cross-workspace signal is visible without opening any card.
14. As an auditor, I do NOT expect a live admin/write/read breakdown of the current Comparison snapshot anywhere in the head bar, so that I know to look at a repo card or project header instead when I need that figure (ADR-0015).
15. As an auditor, I want every repo card and project header to keep showing its own admin/write/read distribution bar and grant counts exactly as today, so that the information dropped from the head bar remains available one level down.
16. As an auditor, I want the filter bar's "All access"/"Changes only" tabs, "Collapse all"/"Reset" controls, and live row-count note to keep working exactly as they do today, so that the v2 visual refresh doesn't regress any existing filter behavior.
17. As an auditor, I want the structural notice strip to keep combining all applicable structural facts (repo absence/arrival, workspace departure/arrival, fetch failures, unresolved memberships) into one truncating prose sentence, so that its existing behavior (PD-19) is preserved under the new visual chrome.
18. As a user, I want a light/dark theme toggle inside the side drawer (alongside credentials/Run/snapshot management), so that I can switch themes from the same place I manage other app-level settings.
19. As a user, I want my theme choice to persist across app launches, so that I don't have to re-select it every time I open the app.
20. As a first-time user who has never set a theme preference, I want the app to default to my OS's light/dark preference (`prefers-color-scheme`), so that the app matches my system out of the box.
21. As a user with the dark theme active, I want every component (head bar, filter bar, notice strip, roster rows, repo cards, tags, chips, side drawer) to render with dark-theme-correct colors and no hardcoded light-only hex values, so that nothing looks broken or mismatched when I switch themes.
22. As a user switching themes mid-session, I want the switch to apply immediately across the whole dashboard without a reload, so that the toggle feels responsive.
23. As a developer maintaining this codebase, I want every component's color values to resolve through `tokens.css` custom properties by name, so that a hardcoded hex is a dark-mode bug I can catch by code review, not just a style-consistency nit (ADR-0005, now load-bearing per ADR-0016).
24. As a developer, I want `tokens.css`'s header comment and ADR-0005/0006/0007's file citations to point at `.references/new-design/` rather than the deleted prototype files, so that future readers aren't sent to files that no longer exist.
25. As a developer, I want `CLAUDE.md`'s "ground truth" list to reference `.references/new-design/` instead of the deleted `dashboard_designs.html`/`standalone/` files, so that the project's own onboarding doc stays accurate.
26. As a developer, I want the roster grid's new v2 track widths and the responsive floor (900px, ADR-0009) to be re-verified together, so that the wider v2 columns don't silently break the existing shed-chrome-first reflow order.
27. As an auditor using the app at a narrow window width, I want the same reflow order as today (repo card grants text sheds first, then the distribution bar, then project meta, then chip labels, then the from-level in transitions — grant-source column never sheds) under the new geometry, so that narrow-window behavior isn't regressed by the token/geometry port.
28. As a developer, I want the v2 design's IBM Plex Sans/Mono font-loading approach reconciled with this app's existing self-hosted `/fonts/*.woff2` convention (PRD §6 forbids runtime CDN calls), so that the port doesn't introduce a Google Fonts dependency the app cannot use.

## Implementation Decisions

- **Scope**: `src/lib/styles/tokens.css` (full token replacement: colors, spacing, geometry, grid track widths, plus new `:root[data-theme="dark"]` block) and its consuming Svelte components: `HeadBar.svelte`, `FilterBar.svelte`, `NoticeStrip.svelte`, `RosterColumnLabels.svelte`, `ProjectSection.svelte`, `RepoCard.svelte`, `RosterRow.svelte`, `SideDrawer.svelte`, plus their paired pure-logic TS modules (`headBar.ts`, `filterBar.ts`, `noticeStrip.ts`, `repoCard.ts`, `rosterRow.ts`, `roster.ts`, `summaryBar.ts`). No `src-tauri` changes — `scope` and `project_fetch_failed` are already correctly computed and serialized by `roster.rs` (verified: both fields exist on the Rust `PrincipalEntry`/`RepoNode` structs with `#[serde(rename_all = "camelCase")]` and are covered by existing `cargo test` cases).
- **Token port**: replace `tokens.css`'s color/spacing/type/geometry custom properties with the v2 values from `.references/new-design/perm-diff.css`, including the `:root[data-theme="dark"]` block verbatim (values only — do not port `perm-diff.css`'s class-based component styles wholesale; keep this app's existing per-component scoped-style structure, per this repo's established pattern of pure-TS-logic + scoped-Svelte-CSS).
- **Font loading**: keep this app's existing self-hosted `/fonts/*.woff2` `@font-face` declarations (already present in `tokens.css`) rather than porting `perm-diff.css`'s Google Fonts `@font-face` src URLs, which point at hosted font subsets not usable per PRD §6's no-runtime-CDN-calls constraint. Font family names/weights must still match what the v2 design specifies (IBM Plex Sans 400/500/600, IBM Plex Mono 400/500/600).
- **Head bar (`HeadBar.svelte`/`headBar.ts`)**: rebuild around the v2 layout — wordmark, baseline/comparison selectors with swap control, delta chips (`+added`/`−revoked`/`~changed`/`↑escalations`, or a `no change` state when the pair has no diff), and the trend line. Retire `SummaryBar.svelte` and `summaryBar.ts`'s `currentStateStats`/`leftClusterLabel` per ADR-0015; `deltaStats` logic is reshaped into the new chip format and consumed by `headBar.ts` (or inlined there — implementer's call whether `summaryBar.ts` is renamed/merged or a new module is added, given both were pure-function modules with no test seam either way).
- **Grant scope suffix (`rosterRow.ts`, ADR-0014)**: `sourceLabel()` takes `scope: GrantScope` as an additional input (alongside the existing `accessType`) and appends `" · project"` when `scope === "Project"`; no suffix for `"Repo"`. The `<span class="source">`'s existing `title` attribute continues to carry the full string so truncation never hides it.
- **Project fetch failure (`roster.ts`, `repoCard.ts`)**: add `projectFetchFailed: boolean` to the `RepoNode` TypeScript interface (mirroring the Rust field already present and serialized). `repoCard.ts`'s tag-derivation logic gains a `project fetch failed` tag, visually and textually distinct from the existing repo-level `fetch failed` tag (both can appear simultaneously on the same card if both are true — they're independent facts per CONTEXT.md). No change to `noticeStrip.ts` — `structuralNotice()` is explicitly not extended with a Project-fetch-failure sentence.
- **Theme (new `theme.ts` + `SideDrawer.svelte` addition)**: a small module exposing current theme (`"light" | "dark"`), a setter, and a read of `localStorage` on init defaulting to `window.matchMedia("(prefers-color-scheme: dark)")` when no stored preference exists. Applies the theme by setting `data-theme` on the root `<html>`/`<body>` element (matching `perm-diff.css`'s `:root[data-theme="dark"]` selector convention) so the switch is instant and CSS-only, no per-component JS branching. Toggle control lives inside `SideDrawer.svelte` alongside credentials/Run/snapshot management (ADR-0010, ADR-0016).
- **Roster grid geometry (`RosterColumnLabels.svelte`, `RosterRow.svelte`)**: adopt the v2 grid track widths and column-label text, preserving the existing seven logical columns (±, level meter, level word, source, user/group, since-baseline transition, notes/tags) and ADR-0009's shed-chrome-first reflow order — re-verify the 900px floor holds with the new (wider) track widths, adjusting breakpoint thresholds if the v2 geometry requires it.
- **Doc citation fixes** (already applied in this session, listed here for completeness/traceability): `CLAUDE.md`'s ground-truth list, `tokens.css`'s header comment, and ADR-0005/0006/0007 now cite `.references/new-design/` instead of the deleted prototype files; ADR-0014/0015/0016 record the three new decisions.

## Testing Decisions

- No `src-tauri`/`cargo test` changes are needed — this spec touches no Rust code. `scope` and `project_fetch_failed` are already covered by existing `roster.rs` test cases on the backend side; this spec only adds frontend consumption of fields that already round-trip correctly today.
- This repo has no JS test runner configured (`package.json` has no test script; `CLAUDE.md` states this explicitly). Consistent with the precedent set by PD-31/32/33 (the most recent frontend-touching work), all pure-TS-logic changes (`rosterRow.ts`'s scope-suffix logic, `repoCard.ts`'s new tag, the new `theme.ts` module, the reshaped delta-chip logic) and all Svelte/CSS changes are verified manually via `pnpm tauri dev`, not automated tests.
- Manual verification should specifically exercise: a Project-level grant row (scope suffix renders, tooltip shows full text), a repo with `project_fetch_failed` true (tag renders, distinct from a repo-level `fetch failed` tag, no notice-strip sentence added), the head bar delta chips in a no-diff (`same` Snapshot pair) state vs. a diff state, the theme toggle (persists across a relaunch, defaults correctly on first launch with no stored preference, applies instantly with no visual glitches in either theme), and the 900px responsive floor with the new track widths (grant-source column still never sheds; shed order for grants-text → distribution bar → project meta → chip labels → transition from-level still holds).
- `pnpm check` (svelte-check/TypeScript) must pass, since the `RepoNode` interface change and `sourceLabel()` signature change are type-level changes that every call site must satisfy.

## Out of Scope

- Any `src-tauri`/Rust changes — `scope` and `project_fetch_failed` are already correct on the backend.
- Introducing a JS test runner (e.g. vitest) — explicitly declined for this spec; stays manual per existing convention.
- PD-31/PD-32/PD-33 (run-progress UI) — unrelated in-flight work, not touched by this spec.
- Any new domain concept or `CONTEXT.md` glossary change — this spec is presentation-layer only; no new terms were introduced during the design-review session that produced it.
- A dedicated scope *column* (rejected in favor of the source-label suffix per ADR-0014).
- A notice-strip sentence for Project fetch failures (rejected per the resolved decision — tag only).
- Retaining any top-level current-state (admin/write/read) breakdown in the head bar (rejected per ADR-0015 — card/project level only).
- Any change to escalation-highlighting's always-on behavior (ADR-0007) — the v2 port must preserve it, not revisit it.
- Any change to PRD §5.4 beyond what ADR-0007 already superseded.
- Rebuilding `perm-diff.css`'s class-based/inline-style component markup verbatim in Svelte — only its token *values* are ported; component structure follows this app's existing scoped-style-per-component pattern.

## Further Notes

- This spec is the direct output of a design-review ("grilling") session that unpacked `.references/new-design/`'s self-extracting bundles, cross-referenced them against the shipped `src/lib/` implementation, `CONTEXT.md`, and ADR-0001 through ADR-0013, and resolved four open contradictions with the user (recorded as ADR-0014, ADR-0015, ADR-0016, plus the project-fetch-failure gap-fix decision). No further interview should be needed before implementation — all user-facing product decisions are already made.
- `.references/new-design/` contains three files beyond `perm-diff.css`: `perm-diff-ledger-light.html`, `perm-diff-ledger-dark.html`, and `perm-diff-token-sheet.html`. All three are self-extracting bundles (~35KB of real markup each, gzipped+base64 inside a `<script type="__bundler/template">` JSON string) — implementers should extract via that mechanism rather than reading the files directly, which are ~500KB+ of bundler/loader boilerplate.
- The v2 design's sample data (`DATA` array embedded in the extracted template) is mock/prototype data for rendering purposes only — it is not a schema and should not be ported.
