## What to build

Foundational plumbing for Display language (PD-79), with no real string content migrated yet:

- Add `svelte-i18n` as a runtime dependency (ADR-0028).
- Add a `language.ts` module mirroring `theme.ts`'s shape exactly: `getLanguage()`, `setLanguage(lang)`, `initLanguage()`. On init, read an explicit stored choice from `localStorage` first; only when nothing is stored, fall back to a one-time OS/webview locale read (`navigator.language`, falling back to `@tauri-apps/plugin-os`'s `locale()` if needed) to pick the closest supported language, defaulting to English if unsupported. An explicit stored choice always wins over a later OS-locale change, same invariant as Theme.
- Wire `initLanguage()` into `+layout.svelte` alongside the existing `initTheme()` call.
- Add a language picker to `AppearancePanel.svelte`, next to the existing Light/Dark segmented control, following the same `getLanguage()`/`setLanguage()` pattern.
- Scaffold English and Brazilian Portuguese (`pt-BR`) catalog files (can be near-empty at this point — just enough real keys to prove the picker actually swaps rendered content somewhere visible).

## Acceptance criteria

- [ ] `svelte-i18n` is installed and initialized against the two catalogs (en, pt-BR)
- [ ] `language.ts` exists with `getLanguage`/`setLanguage`/`initLanguage`, colocated `language.test.ts` passing, mirroring `theme.test.ts`'s cases (stored choice wins and skips OS-locale read; stored choice never overridden by later OS-locale change; falls back to OS-detected language when nothing stored and supported; falls back to English when nothing stored and OS locale unsupported; `setLanguage` persists and updates active catalog)
- [ ] `+layout.svelte` calls `initLanguage()` on startup
- [ ] AppearancePanel has a working language picker that persists across restarts
- [ ] At least one real string renders differently in en vs pt-BR, verified manually via `pnpm tauri dev`
