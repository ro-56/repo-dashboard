## Context

From the 2026-08-01 architecture review (candidate 4, \"Strong\"): `src/routes/dashboard/+page.svelte:168-245` owns a small explicit state machine (`dialogPhase`: review → applying → results, plus `dialogSnapshot`/`dialogResults`/`dialogSourceSnapshotId`/`refreshing`) driven by `confirmApply()` and `refreshAffected()`. Both functions mix `invoke()` Tauri IPC calls, try/catch error handling, and state transitions directly in the Svelte component (lines 201-215, 224-245).

Every pure helper this logic depends on — `canRefresh`, `confirmRows`, `resultRows`, `settleApplied`, `successfulResults`, `toApplyPayload` — is already unit-tested in `pendingEdits.test.ts` (~300 lines). But the orchestration itself has no test coverage and no seam to inject a fake `invoke`: what happens if `apply_pending_edits` throws mid-flight, whether `dialogPhase` correctly reverts to `\"review\"` on error (line 213), whether `refreshing` is reset in the `finally` (line 242).

This mirrors the Rust side's discipline: `lib.rs` documents `run_now`/`refresh_snapshot` as thin wrappers where \"all meaningful logic lives [in collect.rs/refresh.rs] and is covered by cargo test\" — the frontend never made the equivalent move for Apply/Refresh orchestration. Right now this class of bug (stuck `dialogPhase`, `refreshing` never clearing) can only be caught by manually running the app via `pnpm tauri dev`.

Deletion test: extracting `confirmApply`/`refreshAffected` into a `.svelte.ts` module parameterized over an injectable `invoke`-like function would let the state-machine transitions be tested the same way `apply.rs`/`refresh.rs` are — the complexity concentrates in one testable place instead of living only in the render component.

## What to explore

- Decide the module boundary: likely a `.svelte.ts` file (Svelte 5 runes work outside `.svelte` files) that owns `dialogPhase` and friends as exported state, with `confirmApply`/`refreshAffected` taking an injectable `invoke` function as a parameter.
- Check how `ConfirmApplyDialog.svelte` currently reads/reacts to `dialogPhase` etc. — confirm the extraction doesn't just move the untestable coupling into a different file.
- Decide what a fake `invoke` needs to simulate for tests: success, thrown error, and (per the Refresh domain rules in CONTEXT.md) a 401/credential-rejected failure vs. a partial per-target failure.

## Acceptance criteria

- [ ] `confirmApply`/`refreshAffected` (or their replacements) live in a module separate from `+page.svelte`, parameterized over an injectable IPC call.
- [ ] New colocated tests cover: success path phase transitions, error path reverting `dialogPhase` to `\"review\"`, and `refreshing` being reset via `finally` on both success and failure.
- [ ] `+page.svelte` becomes a thin caller of the extracted module, mirroring the existing `lib.rs` thin-wrapper convention.
- [ ] Manually verified via `pnpm tauri dev` that Apply/Refresh behavior (dialog phases, error messages, post-success cleanup) is unchanged.
