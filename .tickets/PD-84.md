## Problem Statement

When auditing a Bitbucket workspace with many repos, a reviewer looking for a specific Principal (a user or group) has no way to jump straight to the repos where that Principal appears — they have to scroll and visually scan every repo card in the Roster tree by hand. This makes "where does X currently have access" a slow, error-prone manual search, especially on larger workspaces where the tree spans dozens or hundreds of repos across many Projects.

## Solution

Add a transient, session-only **Principal search** text input to the FilterBar. Typing a name narrows the Roster tree to only the repos containing at least one `PrincipalEntry` (Direct, Group, or Member alike) whose `Principal.label` matches, case-insensitively, as a substring. Search AND-combines with the existing All access / Changes only view mode — it narrows whichever tab is currently active rather than replacing or disabling it. A repo kept visible only because of a search match auto-expands, the same way a repo carrying a change already does, so the matching Principal is visible immediately without an extra click. Search state is not persisted anywhere — it lives only in the current session's UI state, surviving Baseline/Comparison navigation (like view mode already does) and clearing only via the existing Reset control.

Note: the original request also described excluding a specific noisy Principal (e.g. a permanent "Auditors" group) from view entirely. That is a distinct, standing negative filter rather than a positive search, and is explicitly **out of scope** for this spec — tracked as a separate future ticket.

## User Stories

1. As a reviewer, I want to type a user's or group's name into a search box on the Roster view, so that I can immediately see only the repos where that Principal appears.
2. As a reviewer, I want the search to match case-insensitively, so that I don't have to remember or reproduce a Principal's exact capitalization.
3. As a reviewer, I want the search to match on a substring, so that typing part of a name (e.g. "bob" for "Bob Smith") is enough to find it.
4. As a reviewer, I want the search to match a Principal regardless of whether they hold a Direct, Group, or Member grant, so that I find every way a name shows up in the roster, not just direct grants.
5. As a reviewer, I want a repo to disappear from the tree entirely when none of its Principals match my search, so that I'm not stuck scrolling past irrelevant repos.
6. As a reviewer, I want a repo's *other* Principals to still be visible once the repo itself is shown (not just the matching row), so that I see the matched Principal in the full context of who else has access to that repo.
7. As a reviewer, I want a Project section to disappear entirely when none of its repos match my search, so that empty Project headers don't clutter the narrowed view.
8. As a reviewer, I want search to combine with the Changes only tab, so that I can ask "where does this Principal appear *and* what changed" in one narrowed view.
9. As a reviewer, I want search to combine with the All access tab, so that I can see every repo a Principal is in, changed or not.
10. As a reviewer, I want a repo that's only visible because of my search match to open automatically, so that I see the matching Principal without an extra click per card.
11. As a reviewer, I want to still be able to manually collapse a search-matched repo if I want to, so that my own click always wins over the auto-expand default, same as it already does for changed repos.
12. As a reviewer, I want the "N live · N changed · N rows" count note to reflect only what's currently on screen, so that the note never disagrees with the narrowed tree when a search is active.
13. As a reviewer, I want my search text to persist when I switch the Baseline or Comparison Snapshot, so that I don't have to retype it every time I change which Run pair I'm auditing.
14. As a reviewer, I want my search text cleared when I click the existing Reset control, so that I have one obvious way to get back to the unfiltered view along with view mode and expand/collapse state.
15. As a reviewer, I want a clear "no matches" state when my search text matches nothing anywhere in the tree, so that I know the tree isn't just broken or slow to load.
16. As a reviewer, I want the search text to NOT persist across app restarts, so that stale search state never carries over silently between separate audit sessions.
17. As a reviewer, I want the CSV Roster export to be unaffected by my active search, so that the exported file always reflects the full, unfiltered Comparison Snapshot per the existing Export contract (ADR-0026).
18. As a reviewer, I want the workspace-wide summary figures (total grants, distinct repos, distinct users, Grant/Revoke/Escalation counts) to stay unaffected by my active search, so that those aggregate figures keep meaning "the whole audited workspace," not "whatever I've currently filtered down to."

## Implementation Decisions

- **`src/lib/filterBar.ts`**:
  - New exported predicate `matchesSearch(repo: RepoNode, query: string): boolean` — case-insensitive substring match of `query` against every `PrincipalEntry.principal.label` in `repo.principals`; an empty/whitespace query always matches (no-op when search is inactive).
  - `visibleRepos(project: ProjectNode, mode: ViewMode, query: string): RepoNode[]` gains the `query` parameter, ANDing `matchesSearch` into its existing `repoHasChanges`-based predicate for `"changes"` mode, and applying `matchesSearch` alone for `"all"` mode.
  - `viewCounts(tree: RosterTree, mode: ViewMode, query: string): ViewCounts` gains the `query` parameter so its live/changed/rows figures only count entries belonging to repos that pass `matchesSearch`, keeping the note in sync with the narrowed tree (today it doesn't need repo-level visibility awareness since view mode alone never hides a repo without also zeroing its entries — search does, so this one has to change to stay accurate).
  - `allVisibleOpen` / `visibleRepoCount` callers thread the same `query` through, since they already depend on `visibleRepos`.

- **`src/lib/repoCard.ts`**:
  - `defaultOpen(repo: RepoNode, treeHasChanges: boolean, matchedBySearch: boolean): boolean` gains the `matchedBySearch` parameter, OR'd into its existing condition: `!treeHasChanges || repoHasChanges(repo) || matchedBySearch`.
  - `isRepoOpen(repo, treeHasChanges, matchedBySearch, toggled)` threads the same new parameter through to `defaultOpen`, preserving its existing XOR-against-manual-toggle behavior unchanged — a user's manual collapse still overrides the auto-expand-on-match default exactly as it already overrides the auto-expand-on-change default.

- **`src/routes/dashboard/+page.svelte`**:
  - New `searchQuery = $state("")`, sibling to the existing `viewMode`/`toggledRepos` state, persisting across `navigateToPair` calls (no `$effect` clearing it on `data.comparisonId` change, unlike `pending`).
  - `resetView()` extended to also reset `searchQuery = ""`, alongside its existing `viewMode = "all"` / `toggledRepos.clear()`.
  - All existing call sites of `visibleRepos`, `viewCounts`, `allVisibleOpen`, `visibleRepoCount`, and `isRepoOpen`/`defaultOpen` updated to pass `searchQuery` / the computed `matchesSearch` result through.

- **`src/lib/components/FilterBar.svelte`**:
  - New text input bound to `searchQuery`, placed in the FilterBar alongside the existing All access/Changes only tabs — exact visual placement/styling is an implementation detail for whoever picks up the ticket, not fixed by this spec.
  - Placeholder copy: "Search by name" (new i18n key), following the project's existing `svelte-i18n` convention (ADR-0028) — Bitbucket-sourced Principal labels themselves are never translated, only the input's own chrome.

- **`src/lib/components/ProjectSection.svelte`** / **`RepoCard.svelte`**: no interface changes — they already consume `visibleRepos`/`defaultOpen` results from their callers, so passing an already-search-aware value through requires no new props beyond what's already threaded (`viewMode` today; the same prop-passing shape carries the new query-derived values).

- **`src/lib/emptyState.ts`**: no change needed — its existing generic "no matches" fallback (`noMatchesTitle`/`resetFilters`) was already reserved by an existing code comment for exactly this case and requires no new state.

- **Backend / Rust**: no changes. This is purely a frontend view-state feature over data the Roster tree already carries; `roster.rs`'s tree assembly, `ComparisonSummary`, and `PairStats` are untouched (per their existing documented invariant of never being affected by any view/filter state).

- **`CONTEXT.md`**: already updated with a **Principal search** glossary entry (placed after **Roster tree**) during the design discussion for this feature — no further glossary work needed.

- **ADR**: none. This was evaluated against the project's ADR bar (hard to reverse / surprising without context / result of a genuine trade-off) during design and didn't clear it — the decision is fully captured by the `Principal search` glossary entry instead.

## Testing Decisions

- Tests target the pure functions, not rendered Svelte output, per this project's existing convention (ADR-0017: Svelte component rendering and E2E/visual testing are deferred; `src/lib/*.ts` pure logic gets colocated vitest coverage).
- `src/lib/filterBar.test.ts` (already exists, currently thin — only covers `countNote`) gains cases for:
  - `matchesSearch`: empty query matches any repo; case-insensitive substring match against a Direct/Group/Member Principal's label; no match when the query matches nothing in the repo.
  - `visibleRepos`: query narrows the result in both `"all"` and `"changes"` modes; a repo with a search match but no diff is excluded in `"changes"` mode; a repo with a diff but no search match is excluded when a query is set.
  - `viewCounts`: figures only reflect entries in repos passing both the mode and the query predicates.
- `src/lib/repoCard.test.ts` (already exists) gains cases for:
  - `defaultOpen`/`isRepoOpen`: a repo with no changes but a search match defaults to open; a repo with a search match but manually toggled closed stays closed (manual toggle still wins).
- No new test files — this extends two existing colocated test files rather than introducing a new module, matching the confirmed single-seam approach.
- Manual verification via `pnpm tauri dev` for the FilterBar input itself, the auto-expand visual behavior, and Reset clearing the search box, per this project's stated pattern for Svelte/CSS changes.

## Out of Scope

- **Excluded principal** — the reverse filter (permanently hiding a specific noisy Principal like an "Auditors" group from view) described in the original request. This is a distinct feature with its own open design questions (persistence model, cascade behavior onto a group's derived Member rows, exact UI entry point) and is deferred to a separate future ticket.
- Matching against repo name, Project name, or `Principal.id` — search matches `Principal.label` only.
- Any form of fuzzy, typo-tolerant, or prefix-only matching — substring, case-insensitive only.
- Highlighting the matched row within a visible repo card — only repo-level visibility is affected; all rows in a visible repo render as they do today.
- Any change to the CSV Roster Export (ADR-0026) — export remains a flat, unfiltered, diff-free roster of the Comparison Snapshot regardless of active search.
- Any change to `ComparisonSummary` or `PairStats` (the HeadBar's workspace-wide aggregate figures) — these remain whole-workspace figures, unaffected by search, per their existing documented invariant.
- Persisting search text across app restarts, or any settings/config surface for it.
- Any backend (`src-tauri`) changes — this is frontend-only.
