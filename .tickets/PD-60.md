## What to build

The smallest complete, end-to-end path through the permission-editing feature spec'd in PD-59: edit or remove a Direct grant at Repo scope only, but every layer of the mechanism built for real — no throwaway shortcuts, since Tickets 2 and 3 extend this exact plumbing rather than replace it.

- **`BitbucketClient` trait** (`src-tauri/src/client.rs`): add repo-scope Direct-grant write methods — set (`PUT /2.0/repositories/{workspace}/{repo_slug}/permissions-config/users/{selected_user_id}`) and delete (`DELETE` same path). `RealBitbucketClient` implements them for real; fakes for tests follow the existing `collect.rs` fake-client pattern.
- **New pure Rust module**: `apply_pending_edits(client, workspace, edits: Vec<PendingEditRequest>) -> Vec<ApplyResult>`. Design `PendingEditRequest` (scope: Repo/Project, target: Direct(account_id)/Group(group_slug), repo_project, repo, action: SetLevel(Permission)/Remove) and `ApplyResult` (per-item Ok or a typed error mirroring `ClientError`) to already carry every field Tickets 2/3 will need — but only wire real routing for `Direct` + `Repo` in this ticket; other combinations aren't reachable from the UI yet. Each edit in a batch is applied independently: one failing must not block the rest.
- **Tauri command** `apply_pending_edits`: thin wrapper following the existing `run_now`/`delete_snapshot` convention in `lib.rs`.
- **Frontend `pendingEdits.ts`** (new pure TS module): a keyed map of staged edits (stage a level-change or removal, undo one, clear all), supporting any number of simultaneous pending edits from the start.
- **`rosterRow.ts`**: menu-building function (Read/Write/Admin options highlighting the current effective level, plus Remove) for Direct entries at Repo scope only. Group entries, Project-scope entries, and Member entries get no menu yet.
- **Global "Apply N changes" control**: in the head bar (near the existing delta chips), enabled only when the staged count is > 0 and the Comparison is the latest Snapshot.
- **Confirm dialog**: lists every staged change; Confirm invokes `apply_pending_edits`; Cancel discards nothing. After apply, show per-item success/failure and prompt the user to re-run to see it reflected.
- **Safety gating**: edit controls disabled unless Comparison = latest Snapshot. Pending edits are cleared entirely when a new Run completes (hook into the existing `run_now` invocation in `RunPanel.svelte`).

## Acceptance criteria

- [ ] A Direct grant row at Repo scope shows a menu with Read/Write/Admin options (current level highlighted) and a Remove action.
- [ ] Selecting a level or Remove stages a Pending edit, visibly marked as pending on the row, with an undo control that discards it with no API call.
- [ ] The head bar shows a live count of staged edits and an "Apply N changes" control, disabled at zero.
- [ ] Clicking Apply opens a confirm dialog listing every staged change; Cancel closes it with nothing sent; Confirm calls the Tauri `apply_pending_edits` command.
- [ ] A successful apply calls Bitbucket's real repo-level user permissions-config endpoint (set or delete as appropriate) and reports success per item.
- [ ] A batch with one failing item (simulate via fake client: 403/404/429) still applies the rest, reporting per-item results; the failed item remains staged for retry.
- [ ] After any apply, the user is prompted to re-run — no auto-triggered Run.
- [ ] Edit menus are disabled/absent when the Comparison is not the latest Snapshot.
- [ ] If a new Run completes while edits are staged, all Pending edits are cleared.
- [ ] Group grant rows, Project-scope rows, and Member rows show no edit menu in this ticket.
- [ ] `cargo test` in `src-tauri` covers `apply_pending_edits`'s Direct/Repo routing (set, delete, partial-batch-failure) against a fake `BitbucketClient`, following the existing `collect.rs` fake-client pattern.
- [ ] Colocated `pendingEdits.test.ts` (vitest) covers stage/undo/clear semantics and confirm-dialog view derivation.
- [ ] Colocated additions to `rosterRow.test.ts` cover the new menu-building function for Direct/Repo entries.
- [ ] Confirm dialog markup, head-bar Apply button, and gating/clearing behavior manually verified via `pnpm tauri dev` (ADR-0017 — no Svelte component rendering tests in this pass).
