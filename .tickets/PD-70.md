## What to build

The tracer bullet for Refresh (PD-68): after applying a batch of Pending edits where every successful edit is Repo-scope (Direct or Group), the user can click "Refresh affected" in the Apply results view. This creates a new Snapshot by copying the source Snapshot's data — the one the batch's edits were staged against — filtering out only the touched repos' Repo-scope Direct+Group data, and replacing it with freshly fetched data (using the extracted per-repo fetch function from the prefactor ticket, with live group-membership resolution). Everything else in the Snapshot (every other repo, every Project-scope record, every other status row) is carried over unchanged.

On success, all Pending edits are cleared, the snapshot list is refreshed, and the new Snapshot is auto-selected as the Comparison. If the batch's successful edits include any Project-scope target, Refresh is not offered in this ticket — the existing "please re-run" prompt remains the only path (a follow-on ticket removes this restriction).

A new Rust module owns all the meaningful logic (target derivation, copy/filter/merge, live fetch, failure handling) as one pure async function, cargo-tested against a fake BitbucketClient — same shape and testing convention as the existing Run and Apply orchestration functions. A thin Tauri command wraps it. The frontend's existing pending-edits module gains the pure logic to filter successful results and gate/build the Refresh action; the Apply results dialog gains the button and post-success wiring.

## Acceptance criteria

- [ ] Refresh's core function recomputes only the Repo-scope Direct/Group data for repos named by *successful* ApplyResults, copying every other repo/project's records and statuses verbatim from the source Snapshot.
- [ ] Duplicate targets in one batch (the same repo touched by two or more edits) are fetched exactly once.
- [ ] Failed (`Err`) ApplyResults contribute no target and are excluded from the fetch entirely.
- [ ] A credential-rejected (401) failure on any target aborts the whole Refresh — no new Snapshot is written.
- [ ] A non-401 failure on one target repo records a fetch-failed status (with zero records) for that repo only; every other targeted repo still refreshes and the batch completes.
- [ ] Group membership is resolved live (a fresh membership call) for the touched repos' groups, not copied from the source Snapshot.
- [ ] A batch with zero eligible targets produces a Snapshot that is an exact copy of the source.
- [ ] A thin Tauri command wraps the core function, following the existing thin-wrapper convention (no independent test coverage beyond the underlying module).
- [ ] The Apply results view shows a "Refresh affected" action, enabled only when every successful result in the batch is Repo-scope; hidden/disabled otherwise, falling back to the existing re-run prompt.
- [ ] Clicking it invokes the new command; on success it closes the results view, clears every remaining staged Pending edit, refreshes the snapshot list, and auto-selects the new Snapshot as the Comparison.
- [ ] On failure (e.g. credential rejected), the user sees a clear error and the results view stays open with pending edits intact.
- [ ] The pending-edits module gains the pure filtering/gating logic (which results are eligible, whether Refresh should be offered), covered by colocated unit tests (all-succeeded, all-failed, mixed-scope batches).
- [ ] Manually verified via the dev app run (no component-rendering tests, per the project's existing testing-scope decision).
