## Context

From the 2026-08-01 architecture review (candidate 3, \"Strong\"): `apply_one` in `src-tauri/src/apply.rs:81-128` matches `(GrantScope, EditTarget)` (4 combinations: Repo/Project × Direct/Group) × `EditAction` (Set/Remove) = 8 near-identical branches. Each branch just forwards `edit.repo`/`edit.repo_project`, an id, and an optional `Permission` to one of 8 structurally identical `BitbucketClient` write methods:
`set_repo_direct_permission`, `remove_repo_direct_permission`, `set_project_direct_permission`, `remove_project_direct_permission`, `set_repo_group_permission`, `remove_repo_group_permission`, `set_project_group_permission`, `remove_project_group_permission` (defined on the `BitbucketClient` trait, `src-tauri/src/client.rs`).

The interface (`apply_one`'s signature) is trivial; the real duplication is one layer down, in the trait surface itself — 8 methods that differ only in scope (repo/project) and target (direct/group) where two parameterized methods would do.

Deletion test: inlining `apply_one` into its caller wouldn't help — deleting it just moves the same 8-way match into `apply_pending_edits`. The fix is at the seam between `apply.rs` and `client.rs`, not inside `apply_one`.

## What to explore

- Design the collapsed trait surface: `set_permission(scope: GrantScope, target: EditTarget, key: &str, permission: Permission)` / `remove_permission(scope: GrantScope, target: EditTarget, key: &str)`, or similar — confirm this covers every existing call shape (repo id vs. project key, direct principal id vs. group slug).
- Check every other caller of the 8 existing trait methods (not just `apply_one`) — `collect.rs`/`refresh.rs` only *read* permissions so likely unaffected, but confirm before removing the old methods.
- Decide how the real HTTP adapter and the test fake (used across `apply.rs`'s existing cargo tests) both implement the new narrower trait — two adapters justify keeping this as a seam at all, per `/codebase-design`.
- Check whether Bitbucket's actual REST endpoints differ enough between direct/group or repo/project that a single parameterized method still maps cleanly to one HTTP call each, or whether the URL-building logic needs its own small dispatch internally (that's fine — it just shouldn't leak into the trait's public shape).

## Acceptance criteria

- [ ] `BitbucketClient` exposes a parameterized `set_permission`/`remove_permission` pair (exact names TBD) instead of 8 separate methods.
- [ ] `apply_one` becomes a single call (or a much shorter dispatch) instead of an 8-way match.
- [ ] The existing `cargo test` suite for `apply` passes unchanged in behavior (same requests fired for the same inputs), updated only where the fake client's method names change.
- [ ] No other module depended on the removed 8 individual method names (grep confirms; update any stragglers).
